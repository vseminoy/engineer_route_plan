# Backend

FastAPI-сервис планирования маршрутов выездных инженеров. Контракт API — [`specs/openapi.yaml`](../specs/openapi.yaml) и общие компоненты [`specs/common.yaml`](../specs/common.yaml) в корне репозитория (один контракт для backend и фронтенда), сценарии вызовов — [`src/api/routes/sequence_diagrams.md`](src/api/routes/sequence_diagrams.md).

## Установка и запуск

Команды — из корня репозитория (полный список — `make`):

```bash
make install                   # back/.venv на Python 3.11+ и dev-зависимости
cp back/.env.example back/.env # DATABASE_URL уже указывает на БД стенда; OSRM_URL_CAR/FOOT/BIKE — по необходимости
make run                       # uvicorn --reload на :8002 (RUN_PORT), LOG_FORMAT=console
```

`make run` запускает uvicorn с `--no-access-log`: HTTP-запросы логирует собственная middleware приложения одной структурной записью, а не встроенный access-лог uvicorn. При ручном запуске флаг тоже обязателен.

Весь стенд (БД, миграции, OSRM, backend, фронтенд) поднимается через Docker Compose — `make up`, см. [корневой README](../README.md#быстрый-старт). Локальный `make run` работает с БД поднятого стенда: она опубликована на `127.0.0.1:${DB_PORT}`, схему к этому моменту уже применил сервис `migrate`.

## Устройство

- `src/config.py` — настройки (`pydantic-settings`). `Settings` приложения читаются из переменных окружения и `.env`; `MAX_REQUEST_BODY_BYTES` — предел тела запроса в байтах, по умолчанию 1 МБ. `MigrationSettings` процесса миграций — только из окружения: адрес владельца схемы (`MIGRATION_DATABASE_URL`) в настройки приложения не попадает.
- `src/logging.py` — структурированное логирование (`structlog`): JSON или человекочитаемый вывод по `LOG_FORMAT`, идентификатор запроса и идентификатор длительной операции (`run_id`) как поля записи, а не текст. Строки самого uvicorn выходят в том же формате; его access-лог выключен.
- `src/api/deps.py` — `Depends`-фабрики инфраструктуры: пул соединений БД, клиент OSRM, загрузчик данных, сервис списков региона и сервис статусов заявки (собираются при старте из `data/*.toml` и гео-кэша: битый файл останавливает запуск).
- `src/clients/osrm.py` — клиент OSRM: матрица времени и расстояния в пути (`/table`) и маршрут с геометрией (`/route`) по графу профиля бригады (`car`, `foot`, `bike` — у каждого свой `osrm-routed`; `public_transport` — граф `car`, время × коэффициент). Пары без пути по графу — `None`, отказ OSRM — `503`. Устройство — [`src/clients/sequence_diagrams.md`](src/clients/sequence_diagrams.md).
- `src/app.py` — сборка приложения: настройка логирования, `lifespan` (создание/закрытие пула, клиентов OSRM и Nominatim, сервисов данных; при сбое старта открытое закрывается), закрытие планов, оставшихся `running` от прошлого запуска, до `yield` (`plan_builder.sweep_running_plans`, `failed_reason='shutdown'` — раздел ниже), при остановке — `ProcessSolverPool.shutdown()` без ожидания идущей сборки, регистрация роутеров и обработчиков ошибок, логирующая middleware (по записи `http_request_finished` на запрос; успешная проба `/health` — на уровне `debug`; запрос, не дошедший ни до одного роута, — с `path="<unmatched>"`).
- `src/errors.py` — доменные исключения без знания об HTTP: `InvalidInput` (с `message` или `fields`), `NotFound`, `Conflict`, `DependencyUnavailable` (зависимость недоступна, повтор может помочь), `DatabaseFailure` (БД отвергла запрос, повтор не поможет); у каждого `reason` для лога и бизнес-параметры `params`. Доменные ошибки операций — их наследники.
- `src/api/errors.py` — единственное место, где собирается ответ ошибки. Тело есть только у `400` (`{"message": ...}` или `{"fields": [{"name", "message"}]}`, тексты на русском, не больше 20 полей); `404`, `405`, `409`, `413`, `500`, `501`, `503` — без тела, текст для пользователя строит фронтенд по операции и коду. Ошибка валидации запроса — `400`, а не `422`, запись `request_validation_failed` с именами полей без значений; `DatabaseFailure` — `500` без повторной записи; непредусмотренное исключение — `500` и запись `unhandled_error` со стеком. Бизнес-ошибку логирует маршрут (`<операция>_failed`), ошибку БД или OSRM — место её возникновения; обработчик их повторно не пишет. Все ветки — в [диаграмме](src/api/routes/sequence_diagrams.md#ошибки-любой-операции--единый-обработчик).
- `src/repository/db.py` — `run_query`, граница между репозиторием и драйвером БД: ошибка драйвера пишется в лог одной записью `db_query_failed` (имя запроса и `sqlstate`, без параметров и текста SQL) и превращается в `DependencyUnavailable` (`503`: потеря соединения, нет свободного соединения в пуле, таймаут, взаимная блокировка) или `DatabaseFailure` (`500`: нарушено ограничение, неверные данные).
- `src/domain.py` — общие для сервиса и репозитория значения: навыки, транспорт, статусы заявки, точка (`Point(lat, lon)`, WGS84), черновики региона, бригады и заявки для записи в БД.
- `src/service/loader.py` — загрузка данных региона: файл заявок (CSV или JSON) или встроенный демо-набор (`data/demo/<регион>.csv`) заменяет заявки региона и удаляет его планы; бригады каждого набора региона (демо и всех дополнительных) сохраняются с теми же id, у них обновляются только точки старта. Невалидные строки не загружаются и возвращаются в итоге с номером строки и причиной; файл целиком отклоняется только при неизвестном регионе, нечитаемом или слишком большом файле (больше 500 заявок или 50 колонок) и когда не осталось ни одной заявки. Разбор файла идёт в отдельном потоке, соединение из пула берётся только на запись. Каждый отказ пишется одной записью `data_load_failed` (ошибка входных данных — `warning`, отказ БД или геокодера — `error`), успех — `data_load_finished` со счётчиками строк (`engineers` — сумма бригад всех наборов региона), признаком `engineers_kept` по каждому набору (бригады сохранены или пересозданы) и `wait_ms` — временем ожидания в очередях разбора и записи. Все ветки — в [диаграмме](src/service/sequence_diagrams.md).
- `src/service/ticket_file.py` — чтение файла заявок: кодировка по содержимому (CSV — UTF-8 или Windows-1251, с BOM и без; JSON — UTF-8), колонки по заголовку, пустые строки и служебная строка «Адрес Офиса» отбрасываются до проверки полей (из неё берётся адрес офиса), проверка каждой строки.
- `src/service/ticket_types.py` и `data/ticket_types.toml` — таблица соответствия типов заявок: навык — по «Тип заявки HD», приоритет и минуты на объекте — по «Тип заявки BK», «Авария» в HD — всегда `emergency`; статусы «Статус BK». Новый тип заявки или новый ранг приоритета — строка в TOML, не код.
- `src/service/regions.py` и `data/regions.toml` — регионы (код, название, центр — запасная точка офиса, число бригад демо-набора), смены и точки удалённых городов Подмосковья — общие для генератора демо-набора и всех дополнительных наборов бригад региона. Конфигурация проверяется при чтении: смена не переходит через полночь, бригад на весь день у демо-набора не меньше четырёх.
- `src/service/engineers_generator.py` — генератор бригад набора: детерминирован по `seed` (код региона — для демо-набора, собственный `seed` набора — для остальных); число бригад и доли утренней/вечерней смены — явные параметры набора, конфигурация региона (`regions.toml`) задаёт только смены и точки удалённых городов, общие для всех наборов. Бригады на весь день строятся первыми и вместе несут все навыки и виды транспорта; у каждой бригады 1–3 навыка.
- `src/service/geocoding.py` и `data/geocache.csv` — координаты адресов: адрес в Домодедово, Кашире или Ступино получает точку города из `data/regions.toml`, остальные — точку из гео-кэша, промах — запрос к Nominatim, если он включён (`NOMINATIM_URL`), не больше `NOMINATIM_MAX_LOOKUPS` (50) адресов на загрузку. Кэш покрывает все адреса исходных наборов `docs/synthetic_data` и `docs/control_distribution`, поэтому они грузятся без интернета.
- `src/clients/nominatim.py` — клиент Nominatim: не чаще одного запроса в секунду на процесс, любой ответ, кроме результата поиска, — `DependencyUnavailable`; адрес в лог не пишется.
- `src/repository/region_data.py` и `queries/*.sql` — именованные запросы aiosql и замена данных региона одной транзакцией: планы, строки планов и события перепланирования всех наборов бригад региона удаляются, заявки заменяются; первая загрузка региона создаёт набор бригад `default` (`kind=demo`), при каждой загрузке для каждого набора региона (демо и всех дополнительных) бригады сохраняются, если их состав — название, навыки, транспорт, смена — совпадает с составом генератора, иначе набор создаётся заново; в обоих случаях обновляются только точки старта. `database_errors` в `src/repository/db.py` переводит ошибки драйвера и вне запроса (нет соединения в пуле, сбой на `COMMIT`).
- `src/service/engineer_sets.py`, `src/repository/engineer_sets.py` и `queries/engineer_sets.sql` — дополнительные наборы бригад региона (`GET`/`POST /api/v1/engineer-sets`, `DELETE /api/v1/engineer-sets/{id}`): набор создаётся тем же генератором, что и демо-набор, с явными параметрами (имя, уникальное в регионе; число бригад; доли утренней и вечерней смены; `seed`) — при таких параметрах бригад «на весь день» должно остаться не меньше четырёх, иначе `400` до обращения к БД. `description` в ответе — эти параметры текстом, чтобы различать наборы одного региона на фронте. Удалить можно только не-демо набор — удаление каскадно убирает его планы, строки планов, события перепланирования и бригады одной транзакцией; демо-набор удалить нельзя (`409`).
- `scripts/build_geocache.py` (`make geocache`, нужен интернет) — догеокодирует через публичный Nominatim адреса исходных наборов, которых нет в кэше; ненайденные выводит списком и завершается с ненулевым кодом, после отказа сервиса (403/429) запросы прекращает.
- `alembic/` — миграции схемы БД на чистом SQL (`alembic/versions/`, новая ревизия — `python -m alembic revision -m "<slug>"` из `back/`). `alembic/env.py` берёт адрес из `MIGRATION_DATABASE_URL` и пишет в том же JSON-формате, что приложение. Ревизия создаёт и роли: `app_rw` — приложение, только данные, без права менять схему; `app_ro` — ручные запросы, только чтение; пароли — из `APP_RW_PASSWORD`/`APP_RO_PASSWORD`. Всё время в БД — `TIMESTAMP(0)` без часового пояса, местное время региона. Как стенд применяет миграции — [диаграмма](alembic/sequence_diagrams.md).
- `src/api/body_limit.py` — ASGI-middleware предела тела: `413` без тела и с `Connection: close` сразу по `Content-Length` или при чтении тела без него; тело не буферизуется.
- `src/api/routes/regions.py` — `GET /api/v1/regions`, `/engineers` (принимает необязательный `engineer_set_id`, по умолчанию — демо-набор региона), `/tickets`: регионы из конфигурации, бригады выбранного набора и заявки региона по коду; неизвестный код — `400` у `region`, набор не из этого региона — `400` у `engineer_set_id`, регион без данных — `[]`. Бизнес-ошибку пишет в лог как `list_engineers_failed` / `list_tickets_failed`. Там же `PATCH /api/v1/tickets/{ticket_id}/status` — смена статуса заявки; отказ пишет как `ticket_status_change_failed` (`warning` — недопустимый переход или нет заявки, `error` — отказ БД).
- `src/api/routes/data.py` — `POST /api/v1/data/upload` (multipart: `region`, `tickets_file`; форма разбирается с явными пределами Starlette и проверяется сгенерированной моделью контракта, формат — по расширению `.csv`/`.json`) и `POST /api/v1/data/demo` (JSON `{"region"}`). Сам пишет только `data_upload_failed` (форма не разбирается, не то расширение); ошибки загрузки пишет загрузчик.
- `src/service/region_lists.py` и `src/repository/region_lists.py` — списки региона: код проверяется по конфигурации, переводится в `region_id` одним запросом; бригады читаются по набору (`engineer_set_id` из запроса — с проверкой, что набор принадлежит региону, иначе `400`, — или демо-набор региона по умолчанию), заявки — по `region_id`; строки собираются в доменные `Engineer`/`Ticket` (точка — `Point`, время — наивное; строку заявки разбирает общий `ticket_from_row` из `src/repository/tickets.py`).
- `src/service/ticket_status.py` и `src/repository/tickets.py` — смена статуса заявки диспетчером: таблица допустимых переходов (`NEXT_STATUSES`: вперёд по цепочке `not_sent → sent → en_route → in_progress → completed`, в том числе через шаг; `cancelled` — из любого незакрытого; `overdue` — из `not_sent`/`sent`/`en_route` и обратно в `en_route`/`in_progress`/`completed`/`cancelled`; из `completed` и `cancelled` — никуда). Чтение, проверка и запись — в одной транзакции под блокировкой строки (`SELECT ... FOR UPDATE`), поэтому одновременные запросы к одной заявке проверяются по очереди. Тот же статус — успех без записи; отмена из `en_route`/`in_progress` ставит `cancelled_after_dispatch`. Изменение пишется записью `ticket_status_changed` после фиксации транзакции. Ветки — в [диаграмме](src/api/routes/sequence_diagrams.md#patch-apiv1ticketsticket_idstatus).
- `src/api/routes/not_implemented.py` — заглушка: любой запрос под `/api/v1`, не совпавший с реализованной операцией, получает `501` без тела; регистрируется последней и в контракт не входит.
- `src/api/routes/` — рукописные роутеры; `src/api/schemas/generated/` — Pydantic-схемы, сгенерированные командой `make gen-api` (`models.py` — из `specs/openapi.yaml`, `common.py` — из `specs/common.yaml`, по запуску генератора на файл), не редактируются руками.
- `src/service/solver.py` — построение плана дня трёхфазным (ступенчатым, лексикографическим) решением OR-Tools RoutingModel: одна «машина» на бригаду, узел-заявка допустим только для бригад с нужным навыком и (если задан) транспортом, жёсткое окно на узле, маршрут открытый (обратный путь к старту в занятость не входит). Фаза 1 максимизирует покрытие (штраф отказа строго растёт с приоритетом: авария ≫ подключение ≫ ремонт/дозаказ), фаза 2 минимизирует число бригад без ухудшения покрытия, фаза 3 минимизирует суммарный переезд без ухудшения покрытия и флота — каждая фаза на своей копии модели, с жёстким ограничением по результату предыдущей и стартом с её маршрутов. Время — целые минуты от полуночи дня плана; переезд из матрицы OSRM округляется вверх до минуты. `idle_min` бригады (длина смены минус визиты и переезды) — только для отображения, вне целевой функции всех фаз. Решения не найдено на фазе 1 до её доли предела времени — `INFEASIBLE` без маршрутов, а не пустой план. Чистая функция без обращений к БД или OSRM — вызывающий код и его вызов вне event loop появляются отдельно. Устройство — [`src/service/sequence_diagrams.md`](src/service/sequence_diagrams.md#построение-плана-дня-модель-солвера-ступенчатая-лексикографическая-оптимизация).
- `src/service/baseline.py` — baseline-план: детерминированный проход FCFS по заявкам в порядке входного файла, каждая — первой по порядку подходящей бригаде (навык, транспорт, окно, смена), без сортировки, поиска лучшего варианта и обращения к модели солвера — независимая от OR-Tools реализация с той же формой результата (`DayPlan`/`EngineerRoute`/`Visit`/`SolveStatus`), поэтому план и baseline сравнимы без отдельного маппинга. Результат всегда `OPTIMAL`: решение не ищется, поэтому не может не найтись за отведённое время. Чистая функция без обращений к БД или OSRM. Устройство — [`src/service/sequence_diagrams.md`](src/service/sequence_diagrams.md#построение-плана-дня-baseline-fcfs).
- `src/service/explain.py` — атрибуция причины отказа и текст объяснения по каждой строке плана (солвера или baseline). Атрибуция — независимая от построившего план алгоритма последовательная проверка по группам ограничений (навык → транспорт → окно/смена → «все технически подходящие заняты»): берётся первая группа, после которой не осталось ни одного кандидата, без учёта фактического маршрута бригады в плане — только её точка старта и смена. Тексты — на естественном языке (навык, окно, транспорт, время в пути или число подходящих бригад), без терминов солвера. Чистая функция без обращений к БД, OSRM и OR-Tools; `tickets`/`engineers`/`matrices` должны быть тем же входом, что был у алгоритма, построившего план. Устройство — [`src/service/sequence_diagrams.md`](src/service/sequence_diagrams.md#атрибуция-причины-отказа-и-генерация-объяснений).
- `src/service/plan_builder.py` — оркестратор `POST /api/v1/plan/build`: `enqueue` проверяет вход, резолвит набор бригад (`engineer_set_id` из тела запроса — с проверкой принадлежности региону, или демо-набор региона по умолчанию) и вставляет план со `status=running` вместе с `engineer_set_id` в теле ответа, `build` — OSRM, солвер (в `ProcessSolverPool`'s `ProcessPoolExecutor(max_workers=1)`, общем на всё приложение) или baseline, `explain` и персист — в фоновой задаче после ответа `202`. Никогда не бросает исключение наружу из `build`: любая ошибка становится `status=failed` с причиной на самой строке плана. Постановка `or_tools`-вызова на исполнитель сериализована `_or_tools_lock`, а сам вызов обёрнут watchdog'ом (`asyncio.wait_for`, `SOLVER_TIME_LIMIT_S + SOLVER_WATCHDOG_MARGIN_S`): зависший воркер `ProcessSolverPool.restart()` убивает и пересоздаёт исполнитель, план — `failed_reason='timeout'`. Модульная `sweep_running_plans` (вызывается из `app.py`'s `lifespan` до `yield`, не из этого класса) закрывает планы, оставшиеся `running` после нештатной остановки, `failed_reason='shutdown'`, по всем регионам сразу. `src/service/plan_reader.py` — чтение плана для `GET /api/v1/plan/{plan_id}`: ответ всегда несёт `engineer_set_id`, для которого план построен; `running`/`failed` отдаются почти пустыми, `done` — сохранённые строки `assignments` собираются в маршруты каждой бригады набора (включая незадействованные, с пустым маршрутом), простой бригады пересчитывается из смены и визитов при чтении, обязательные `metrics` (число задействованных бригад, суммарный и по бригадам пробег, число назначенных/неназначенных, простой по бригадам) считаются из уже собранных маршрутов, не хранятся отдельно. `compare` (`GET /api/v1/plan/{plan_id}/compare`) читает оба плана через тот же `get` — план из пути первым, план-baseline только если первый готов — сравнивает их только при одинаковом `engineer_set_id` (иначе `400`) и сравнивает `engineers_used`/`total_distance_km` (`idle_time` в сравнение не входит, оно только для отображения). Устройство — [`src/service/sequence_diagrams.md`](src/service/sequence_diagrams.md#сборка-плана-post-planbuild), [`src/api/routes/sequence_diagrams.md`](src/api/routes/sequence_diagrams.md#post-apiv1planbuild).
- `src/service/replan.py` — синхронный пересчёт части плана-родителя одним событием (`POST /api/v1/plan/{plan_id}/replan`): новый план всегда наследует `engineer_set_id` плана-родителя — кандидаты ищутся среди бригад того же набора, перепланирование никогда не меняет набор. Contract Net Protocol без повторного запуска солвера — точечная вставка в уже стоящий маршрут бригады-кандидата, а не полный пересчёт дня. `new_urgent_ticket` — заявка вставляется сервером (`required_skill=emergency`, `priority=1`, `duration_min=80`), кандидаты — бригады с этим навыком, победитель — минимальное время прибытия среди успевающих в `reaction_min` от `triggered_at` (иначе среди всех); если у победителя нет позиции без нарушения окон уже стоящих заявок — вытеснение глубиной 1 (снимается не начатая заявка низшего приоритета, разыгрывается среди остальных бригад без второго вытеснения). `new_ticket` (необязательная возможность) — новая обычная заявка в течение дня: `required_skill`/`priority`/`duration_min` берутся таблицей соответствия типов заявок (`type_bk`/`type_hd`), окно — своё, от клиента. Нет объявления и нет вытеснения: кандидаты с этим навыком (и транспортом, если задан) ищут в своём фактическом маршруте свободный интервал, куда заявка входит в своё окно, не отодвигая ни один уже стоящий визит — побеждает интервал с минимальным временем прибытия; ничего в найденном маршруте, кроме самой вставки, не пересчитывается, только сдвигается `sequence_no`. `ticket_cancelled` — заявка снимается с маршрута бригады, её оставшиеся визиты сдвигаются пересчётом. Состояние на `triggered_at`: `completed`/`cancelled` исключены, `in_progress` заморожена (бригада свободна не раньше её планового конца) и переносится в новый план без изменений — она открыта, только не подвижна. Каждый вызов — новый план с `parent_plan_id`: у не затронутых событием бригад строки `assignments` копируются из плана-родителя, у затронутых — пересчитываются целиком; `diff` в ответе — отдельное сравнение новых строк со старыми, не то же самое, что объём персиста. Устройство — [`src/service/sequence_diagrams.md`](src/service/sequence_diagrams.md#перепланирование-contract-net), [`src/api/routes/sequence_diagrams.md`](src/api/routes/sequence_diagrams.md#post-apiv1planplan_idreplan).

## Технический долг

- **С включённым Nominatim загрузки делят очередь геокодера.** Промахи гео-кэша всех
  загрузок идут в Nominatim через один клиент, по запросу в секунду; загрузка с 50 промахами
  (предел на загрузку) длится минуты, остальные с промахами ждут её, а отключившийся клиент
  работу не отменяет — загрузка доходит до конца и сохраняет данные. Для демо-стенда это
  приемлемо: Nominatim по умолчанию выключен, гео-кэш покрывает все исходные наборы. Для
  открытого стенда с внешним геокодером нужны предел одновременных загрузок (отказ `409`) или
  фоновая загрузка с опросом статуса.
- **Номер заявки не уникален в регионе.** `tickets.external_id` — поле «Заявка» входного файла, ограничения уникальности на нём нет, и загрузчик повторы не отсекает: каждая строка файла становится отдельной записью со своим `id`. Так сделано, потому что работаем на синтетических и контрольных наборах: в них номер заявки может повторяться (в контрольном наборе Юго-Востока одна заявка встречается дважды — отменённой в одном окне и выполненной в другом), и правила уникальности для таких данных не определены. Внутри приложения заявку идентифицирует только `id`. Для реальных данных нужно решить, что значит повтор номера (перенос, дубликат выгрузки, новая заявка), и закрепить это ограничением `UNIQUE (region_id, external_id)` и правилом загрузчика.
- **Ожидание блокировки строки не ограничено по времени.** Смена статуса ждёт `SELECT ... FOR UPDATE` сколько угодно и всё это время держит соединение пула; у роли `app_rw` нет `lock_timeout` и `idle_in_transaction_session_timeout`. Сейчас блокировку держат две короткие операции по ключу, без внешних вызовов, так что ожидание — миллисекунды. Зависшая чужая транзакция на строке `tickets` заняла бы пул, и остальные запросы получили бы `503` через 30 с ожидания соединения. Закрыть вместе с перепланированием, которое тоже будет брать строки заявок под блокировку: `ALTER ROLE app_rw SET lock_timeout = ...` миграцией (истечение — `503`).
- **Операция над заявкой — в роутере регионов.** `PATCH /api/v1/tickets/{ticket_id}/status` лежит в `src/api/routes/regions.py` рядом с `GET /tickets` и использует его преобразование заявки в ответ; когда у заявки появятся другие операции, их место — отдельный `src/api/routes/tickets.py`.
- **Солвер держит GIL на весь поиск.** `SolveWithParameters` — нативный вызов OR-Tools, который GIL не освобождает: запуск через `run_in_executor`/поток не отдаёт event loop другим запросам на время предела поиска, только отдельный процесс это делает — `plan_builder.py` запускает его в `ProcessSolverPool`'s `ProcessPoolExecutor(max_workers=1)`, общем на всё приложение, так что конкурентное построение встаёт в очередь на `_or_tools_lock`, а не запускается параллельно вторым процессом. Ступенчатая (лексикографическая) оптимизация строит и решает модель трижды за одно построение плана (своя копия на фазу): на максимальном входе (30 бригад, 500 заявок, предел 10 с) фактическое время `solve_day` — около 12 с, то есть предел времени превышается примерно на 20% за счёт сборки трёх моделей (у одного прогона — около 3%) — это стоит учитывать при выборе `SOLVER_TIME_LIMIT_S`. Зависший солвер убивает watchdog (`SOLVER_TIME_LIMIT_S + SOLVER_WATCHDOG_MARGIN_S`, план — `failed_reason='timeout'`); план, оставшийся `running` из-за нештатной остановки backend, закрывает `failed_reason='shutdown'` sweep при следующем старте (`src/service/plan_builder.py` раздел выше) — перестроить план в обоих случаях можно только новым `POST /plan/build`, автоматического возобновления фонового построения нет.
- **`POST /plan/build` не ограничивает число одновременно поставленных в очередь построений.** Ничто не мешает клиенту вызвать эндпоинт много раз подряд: каждый вызов читает заявки и бригады региона, строит матрицы OSRM и ставит фоновую задачу в очередь единственного исполнителя, при этом `tickets`/`engineers`/матрицы каждой задачи держатся в памяти до её выполнения — это способ исчерпать память, которого не покрывает ни размер одного построения (раздел «Время в пути»), ни серилизация самого солвера (пункт выше). Аутентификации, которая ограничила бы, кто и как часто вызывает эндпоинт, в проекте нет намеренно; предел на число заявленных, но ещё не завершённых построений (по региону или глобально, `409` на превышении) устранил бы это, но такое поведение — часть контракта и требует отдельного решения, а не однострочной правки.
- **`baseline.py`, `explain.py` и `plan_reader.py` дублируют формулу длины смены (`_shift_min`/`_shift_min`-подобный код), `baseline.py`/`explain.py` — ещё и проверку размера матриц (`_validate`).** Правка одной формулы (например, длины смены) может попасть не во все три файла. Вынос в нейтральный модуль (например, `src/service/plan_common.py`), от которого одинаково зависят все три, устранил бы риск расхождения копий, не нарушая независимость `baseline.py` от модели солвера — стоит обсудить отдельным небольшим изменением.
- **`POST /api/v1/engineer-sets` не ограничивает число наборов на регион.** Каждый вызов можно повторять произвольное число раз — как и у `POST /plan/build` (пункт выше), аутентификации, которая ограничила бы вызывающего, в проекте нет намеренно. Набор — до 30 строк `engineers` плюс одна строка `engineer_sets`, так что раздувание таблиц медленнее, чем у `plan/build`, но того же рода; мягкий предел числа наборов на регион устранил бы это, но требует отдельного решения по контракту (код ошибки, значение предела).
- **Название набора бригад (`EngineerSetCreateRequest.name`) не обрезается от пробелов.** Контракт ограничивает длину (1–100 символов), но не запрещает имя из одних пробелов или с ведущими/замыкающими — такое имя проходит `UNIQUE (region_id, name)` как отдельное значение и может путать при выборе набора на фронте (`" default"` ≠ `"default"`). Не влияет на корректность или безопасность (значение параметризовано, нигде не исполняется), исправляется тримом на уровне сервиса при необходимости.
