# Интеллектуальный сервис планирования маршрутов выездных инженеров

Прототип для хакатона «Билайн Бизнес» — автоматическое распределение заявок между выездными бригадами, построение маршрутов и перепланирование при внештатных событиях.

Полный комплект технической документации (бизнес-требования, ТЗ, спецификации бэкенда/фронтенда, словарь данных, алгоритм) — [`docs/bft/`](docs/bft/00_index.md).

## Быстрый старт

Нужны Docker с Compose, GNU Make, `curl` и Python 3.11+. Команды выполняются из корня репозитория; `make` без аргументов печатает список всех целей.

```bash
make up       # создать .env из .env.example (если его нет) и поднять стенд
make smoke    # проверить стенд: /health → 200, /api/v1/regions → 200
make logs s=backend
make down     # остановить; make reset — ещё и удалить данные БД и графы OSRM (спросит подтверждение)
```

Разработка backend:

```bash
make install  # back/.venv с dev-зависимостями; на macOS системный python3 — 3.9: make install PYTHON=python3.11
make check    # lint + typecheck + unit-тесты + проверка комментариев
make gen-api  # перегенерировать Pydantic-схемы после правки specs/openapi.yaml или specs/common.yaml
make run      # backend на :8002 с автоперезагрузкой; сначала cp back/.env.example back/.env
make geocache # догеокодировать новые адреса исходных наборов в back/data/geocache.csv (нужен интернет)
```

Инструменты берутся из `back/.venv`; другое окружение — `make check PY=/path/to/python`. Фронтенд в режиме разработки проксирует `/api` на `:8001` (backend стенда); на `make run` — `VITE_BACKEND_ORIGIN=http://localhost:8002`.

## Запуск стенда (Docker Compose)

Без Make:

```bash
test -f .env || cp .env.example .env
docker compose up -d --build
```

- Интерфейс и API — http://localhost:8080 (`FRONTEND_PORT`): nginx отдаёт фронтенд и проксирует `/api` и `/health` в backend. Стенд слушает только `127.0.0.1`; открыть его в локальную сеть — `FRONTEND_BIND=0.0.0.0` в `.env` (API без аутентификации: любой в сети сможет менять данные стенда).
- Backend напрямую — http://127.0.0.1:8001 (`BACKEND_PORT`), например `/docs`.
- Ещё не реализованные операции `/api/v1/...` отвечают `501` без тела — фронтенд показывает «Эта функция ещё не реализована».
- Первый запуск `osrm-prepare` строит из выгрузки OSM в репозитории (`osrm/moscow-oblast.osm.pbf`, см. «Данные OSM») три графа дорог — `car`, `foot`, `bike`; каждый обслуживает свой сервис (`osrm-car`, `osrm-foot`, `osrm-bike`). Это около 16 минут и около 5 ГБ на диске. Docker нужно выделить не меньше 8 ГБ памяти: `osrm-extract` берёт до 3,8 ГБ (при нехватке завершается с кодом 137), три `osrm-routed` в работе — около 3,4 ГБ. `docker compose up -d` возвращает управление только после окончания подготовки; этапы видны в `docker compose logs -f osrm-prepare`. Графы хранятся в volume `osrm-data`; при следующих запусках подготовка графа пропускается, пока не изменится файл выгрузки (сравнивается его контрольная сумма). Backend и фронтенд работают, не дожидаясь OSRM.
- Схему БД применяет разовый сервис `migrate` (`alembic upgrade head`) при каждом `make up`; backend стартует только после его успешного завершения. Новая ревизия подхватывается после пересборки образа — тем же `make up` (без перезапуска приложения — `docker compose run --rm migrate`). Текущая ревизия записана в таблице `alembic_version` БД; упавшую миграцию видно как `Exited (1)` у `migrate` в `docker compose ps -a`, причина — в `docker compose logs migrate`.
- БД для клиента на этой машине — `127.0.0.1:5432` (`DB_PORT`), база `POSTGRES_DB`. Для ручных запросов — роль `app_ro` (только чтение, пароль `APP_RO_PASSWORD`); приложение работает под `app_rw`, у которой нет права менять схему. Без клиента: `docker compose exec db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"`.
- Стенду не нужен интернет: выгрузка OSM лежит в репозитории, координаты адресов демо-наборов и исходных файлов лежат в `back/data/geocache.csv`. Внешний геокодер Nominatim для адресов вне кэша по умолчанию выключен; включить — `NOMINATIM_URL=https://nominatim.openstreetmap.org` в `.env`.
- Всё время в БД и API — местное время региона без часового пояса; пояс процессов стенда задаёт `TZ` (по умолчанию `Europe/Moscow`).
- `docker compose down` останавливает стенд, `docker compose down -v` — ещё и удаляет данные БД и графы.

### Smoke-проверка

Коды ответов проверяет `make smoke`; вручную, с телом, заголовками и логами:

```bash
curl -i http://localhost:8080/health           # 200 {"status": "ok", ...}
curl -i http://localhost:8080/api/v1/regions   # 200, список регионов, заголовок X-Request-ID
docker compose logs --no-log-prefix backend    # по одной JSON-записи на строку, у http_request_finished есть request_id
```

## Загрузка данных

Регион — отдельный сценарий: свои заявки и бригады, код региона (`east`, `south_east`,
`south_center`) — из `GET /api/v1/regions`. Загрузка заменяет заявки региона и удаляет его
планы; бригады региона создаются при первой загрузке и дальше сохраняются с теми же `id`,
у них обновляются только точки старта. Ответ загрузки — число бригад и заявок, пропущенные
строки (пустые и строка адреса офиса) и невалидные строки с номером, колонкой и причиной.

```bash
# встроенный демо-набор региона (без интернета)
curl --noproxy '*' -X POST -H 'Content-Type: application/json' \
  -d '{"region": "east"}' http://localhost:8080/api/v1/data/demo
# свой файл заявок: CSV (UTF-8 или Windows-1251, разделитель «;») или JSON (UTF-8)
curl --noproxy '*' -F region=south_east \
  -F "tickets_file=@docs/synthetic_data/Юго-восток Синтетические данные.csv" \
  http://localhost:8080/api/v1/data/upload
# бригады и заявки региона
curl --noproxy '*' 'http://localhost:8080/api/v1/engineers?region=east'
curl --noproxy '*' 'http://localhost:8080/api/v1/tickets?region=east'
```

Пределы: тело запроса — 1 МБ (`MAX_REQUEST_BODY_BYTES`, больше — `413`), в файле — не больше
500 заявок и 50 колонок, адрес — до 300 символов, остальные поля — до 200. Формат колонок и
ответов — `specs/openapi.yaml`, ветки ошибок — `back/src/api/routes/sequence_diagrams.md`.

## Статус заявки

Диспетчер отмечает ход заявки по сообщению бригады:

```bash
curl --noproxy '*' -X PATCH -H 'Content-Type: application/json' \
  -d '{"status": "en_route"}' http://localhost:8080/api/v1/tickets/1/status
```

Статусы идут по цепочке `not_sent → sent → en_route → in_progress → completed`, вперёд можно и
через шаг. `cancelled` — из любого незакрытого статуса, `overdue` — из `not_sent`, `sent`,
`en_route`, а из него — в `en_route`, `in_progress`, `completed` или `cancelled`. `completed` и
`cancelled` — закрытые статусы: заявку больше нельзя перевести, и в перепланировании она не
участвует. Недопустимый переход — `400` с текстом, статус не меняется; тот же статус — `200` без
изменений. Отмена из `en_route` или `in_progress` отмечается у заявки: выезд бригады уже потрачен.
Таблица переходов и ветки ошибок — в `back/src/api/routes/sequence_diagrams.md`.

## Данные OSM

`osrm/moscow-oblast.osm.pbf` — дороги Москвы и Московской области из выгрузки Центрального ФО
Geofabrik (`central-fed-district-latest.osm.pbf`, данные на 2026-09-24 20:21 UTC). Прямоугольник
35.1–40.3° в. д., 54.2–57.0° с. ш. (с краями соседних областей); оставлены только объекты, нужные
графам: дороги, паромы, платформы, пирсы, разводные мосты, парковки и запреты поворотов. Без
зданий, адресов, природы и истории правок файл занимает 73 МБ вместо 367 МБ. На проверочных
пешеходных маршрутах и матрице (`foot`, `/route` и `/table`) время и расстояние совпадают с
неурезанной выгрузкой до метра.

sha256 файла: `e91b5df5694f51193130b75f7b2e3ee8d7d28acb44a1eac90d8909d9de4a460d`.

Обновить выгрузку (нужен `osmium-tool`, например `brew install osmium-tool`). Промежуточные файлы
(~1 ГБ и ~370 МБ) пишутся во временный каталог, не в репозиторий:

```bash
work=$(mktemp -d)
url=https://download.geofabrik.de/russia/central-fed-district-latest.osm.pbf
curl -L -o "$work/central-fed-district-latest.osm.pbf" "$url"
curl -L -o "$work/central-fed-district-latest.osm.pbf.md5" "$url.md5"
(cd "$work" && md5sum -c central-fed-district-latest.osm.pbf.md5)
osmium extract -b 35.1,54.2,40.3,57.0 --strategy complete_ways \
  -o "$work/region.osm.pbf" "$work/central-fed-district-latest.osm.pbf"
osmium tags-filter "$work/region.osm.pbf" \
  w/highway w/route=ferry w/railway=platform w/public_transport=platform \
  w/man_made=pier w/bridge=movable w/amenity=parking r/type=restriction \
  -f pbf,add_metadata=false -o osrm/moscow-oblast.osm.pbf --overwrite
rm -r "$work"
shasum -a 256 osrm/moscow-oblast.osm.pbf   # записать в этот раздел
```

Файл не должен превышать 100 МБ — предел GitHub; с 50 МБ `git push` выводит предупреждение. Каждое
обновление навсегда добавляет ~73 МБ в историю репозитория, поэтому выгрузку обновляют редко.
Графы пересоберутся при следующем `make up`.

## Допущения

### Время на объекте и время в пути

Источник: [`docs/Нормативы.xlsx`](docs/Нормативы.xlsx) и условие **conditions.md №45**:

> «Норматив на дорогу — величина переменная. 20 минут нужны для того, чтобы заявка при постановке в график бронировала время. При распределении эти 20 минут заменяются на реально рассчитанное время в пути».

Отсюда два разных, не взаимозаменяемых понятия времени:

1. **`duration_min` — время на объекте:** «Технические работы» + «Документы» по нормативу типа работ, без дороги. Для аварии — 80 минут.
2. **Время в пути** — всегда расчётное: по графу дорог через OSRM, для пары точек и профиля транспорта бригады, в минутах с округлением вверх. Им считаются расписание, пробег и метрики плана — и при построении плана, и при перепланировании.

Норматив «20 минут на дорогу» — только резерв, которым заявка бронирует время в графике, пока маршрута ещё нет (параметр `travel_reserve_min`). Для аварии 100-минутный норматив (BR-14) — это дорога + 80 минут на объекте, отсчёт с момента фактического поступления заявки: при бронировании 20 + 80, в плане — расчётное время в пути + 80. Срок реакции на аварию задаёт целевое время от поступления до прибытия бригады — 1–2 часа (BR-33, параметр `reaction_min`, по умолчанию 120 минут).

Время в пути по видам транспорта:

- `car`, `foot`, `bike` — у каждого свой граф дорог OSM со своими правилами: пешеходу и велосипеду открыты дорожки и дворы, закрытые машине, а велосипеду и машине — разные классы дорог; скорость — по профилю OSRM. Поэтому на короткой дистанции велосипед и пешеход проходят меньше километров, чем машина, но тратят больше времени.
- `public_transport` — отдельного графа нет: время на машине × `PUBLIC_TRANSPORT_FACTOR` (по умолчанию 1,5) — усреднённая поправка на пересадки, ожидание и пешие участки; расстояние — как у машины.
- Если между двумя точками нет пути по графу, переход между ними невозможен; расстояние по прямой не подставляется.

Подробности и таблицы с разбивкой по типам заявок — [`docs/bft/07_data_dictionary.md` §5](docs/bft/07_data_dictionary.md#5-нормативы-длительности-работ-docsнормативыxlsx-минуты) и [`docs/bft/05_spec_backend.md` §8](docs/bft/05_spec_backend.md#8-модуль-расчёта-нормативов-длительности).

### Бригады и смены

Во входных файлах только заявки, поэтому бригады региона создаёт генератор демо-бригад (`back/src/service/engineers_generator.py`, параметры — `back/data/regions.toml`). Он детерминирован: для региона всегда один и тот же состав бригад. Бригады создаются при первой загрузке данных региона и сохраняются при следующих с теми же id; повторная загрузка обновляет у них только точки старта (офис и удалённые города — по файлу), заменяет заявки и удаляет планы региона.

- Число бригад — ориентир контрольного распределения: Восток 13, Юго-Восток 12, Югоцентр 11. В регионе не больше 30 бригад.
- У бригады от 1 до 3 навыков, у бригад на весь день вместе есть все три навыка и все четыре вида транспорта.
- Смены — в пределах одних суток: утренняя 10:00–18:00 и вечерняя 15:30–23:30 — по четверти бригад региона, остальные (не меньше половины и не меньше четырёх) — весь день, 10:00–23:30. Конец 23:30 — чтобы работа, начатая в конце последнего окна (22:00), успевала закончиться: на объекте не больше 80 минут. В контрольном распределении одна бригада берёт окна с 10:00 до 22:00, поэтому смена на весь день преобладает.
- Бригады стартуют из офиса региона (адрес — служебная строка файла, без неё — центр региона); для каждого удалённого города Подмосковья среди районов заявок (Домодедово, Кашира, Ступино) одна бригада на весь день стартует из точки этого города.

### Координаты адресов

Координат во входных файлах нет. Адреса исходных наборов геокодированы один раз через Nominatim (OpenStreetMap) и лежат в `back/data/geocache.csv`; запрос строится из улицы и дома без квартиры. Адрес «Самаркандский б-р, кв-л 137а, к5» Nominatim не находит — для него записана точка бульвара. Адреса в Домодедово, Кашире и Ступино получают одну точку города из `back/data/regions.toml`: по названию города Nominatim возвращает, например, аэропорт. Заявка, для адреса которой точка не нашлась, не загружается.

### Заявки из файла

- Файл — заявки одного региона на один день, не больше 500 заявок (пустые строки и строка адреса офиса не считаются). Бригада за день выполняет около 12 заявок (в контрольном распределении — до 14), 30 бригад — около 300; 500 оставляет запас на сценарии нехватки бригад. Все заявки дня и старты бригад идут в одну матрицу времени в пути (до 530 точек): на графе `bike` она считается до ~26 с, предел ожидания ответа OSRM — 60 с (`OSRM_TIMEOUT_S`).
- Тип заявки → навык, приоритет и время на объекте — таблица `back/data/ticket_types.toml` (по словарю данных, раздел 3).
- Статус — из колонки «Статус BK», если она есть (контрольное распределение), иначе `sent`.
- Момент поступления заявки из файла — начало суток её окна: все заявки файла известны на начало дня.
- Номер заявки («Заявка») не обязан быть уникальным: в контрольном наборе Юго-Востока одна заявка встречается дважды, каждая строка — отдельная заявка (технический долг, см. [`back/README.md`](back/README.md#технический-долг)).
