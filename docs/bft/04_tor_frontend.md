# Техническое задание — Frontend

Ссылки: бизнес-требования — [`01_business_requirements.md`](01_business_requirements.md), стек — [`02_tech_stack.md`](02_tech_stack.md), точная спецификация экранов/компонентов — [`06_spec_frontend.md`](06_spec_frontend.md).

## 1. Цель модуля

Дать диспетчеру веб-интерфейс, который за один сценарий демонстрации (ТЗ п.4, 5–7 минут) показывает: загрузку данных, построенный план на карте, объяснение по конкретной заявке, реакцию на событие перепланирования с наглядным diff, сравнение метрик с базовым алгоритмом. Интерфейс должен быть понятен без обращения к коду (NFR-07) и адаптирован под мобильные устройства (FR-31).

## 2. Пользовательский сценарий (основной путь, соответствует демо-сценарию ТЗ п.4)

1. Диспетчер загружает/открывает тестовый набор данных (регион, день).
2. Запускает автоматическое планирование.
3. Видит на карте заявки и маршруты бригад, и рядом — сводку «кто/куда/когда».
4. Открывает одну заявку → видит объяснение, почему она назначена именно этой бригаде (или почему не назначена).
5. Добавляет срочную заявку / отменяет заявку / делает бригаду недоступной (одно событие).
6. Запускает перепланирование → видит, что именно изменилось относительно предыдущего плана.
7. Сравнивает результат с базовым (наивным) распределением по двум обязательным метрикам.

## 3. Состав экранов/представлений (обязательный MVP)

| Экран/блок | Назначение | Требования |
|---|---|---|
| **Загрузка данных** | Выбор региона/дня, загрузка CSV/JSON или демо-набора | FR-01 |
| **Карта плана** | Точки заявок (цвет/иконка по статусу и приоритету), маршруты бригад полилиниями (цвет на бригаду), старт бригады отдельным маркером | FR-08 |
| **Панель сводки плана** | Список бригад: количество заявок, суммарное время, пробег; список неназначенных заявок с причиной | FR-09, FR-10, FR-11 |
| **Карточка/модалка заявки** | Детали заявки + блок объяснения назначения (или причины отказа) простым языком | FR-15 |
| **Панель метрик и сравнения** | Обязательные метрики основного плана vs baseline; отдельным блоком — простой бригады (справочно, без влияния на план); дополнительно — балансировка загрузки, если включена (FR-21) | FR-11, FR-12, FR-23, FR-21 |
| **Панель событий перепланирования** | Форма создания одного из трёх событий (новая срочная заявка / отмена / недоступность бригады), кнопка «Перестроить план» | FR-13, FR-14 |
| **Diff-вид после перепланирования** | Визуальное выделение изменившихся назначений/маршрутов относительно предыдущего плана (например, подсветка на карте + список изменений) | FR-16, FR-22 |

## 4. Дополнительные экраны/элементы (не блокируют MVP)

- Ручное переназначение заявки drag-and-drop или через меню (FR-24).
- История нескольких последовательных сценариев событий за сессию (FR-25).
- Индикатор риска опоздания/SLA на карточке заявки (FR-26).

## 5. Требования к адаптивности

- Раскладка mobile-first: на ширине ≤768px карта и панели складываются в одну колонку с вкладками/аккордеоном вместо side-by-side.
- Все интерактивные элементы (кнопки событий, открытие карточки заявки) доступны с тач-управления без hover-зависимых действий.
- Карта остаётся полноэкранной/приоритетной на мобильном виде, панели — раскрываемые снизу (bottom sheet) или по вкладкам.

## 6. Взаимодействие с backend

- Все данные — через REST API backend (см. [`05_spec_backend.md`](05_spec_backend.md#4-api-контракт)); фронтенд не выполняет собственных расчётов маршрутов/назначений.
- Состояние плана хранится на backend; фронтенд запрашивает актуальный план и результаты перепланирования по идентификатору сессии/запуска (`plan_id`).
- Ошибки backend (невалидный файл, недоступен OSRM и т.п.) отображаются диспетчеру понятным сообщением, а не как технический stack trace.

## 7. Нефункциональные требования к frontend

- Время отклика UI на действия пользователя (не считая серверного пересчёта) — не более 300 мс воспринимаемой задержки (skeleton/loader на время ожидания ответа backend).
- Карта и панели должны корректно работать в последней версии Chrome/Firefox/Safari (десктоп и мобильные).
- Объяснения и причины отказа отображаются полным текстом без обрезки — не более технического жаргона (NFR-01, NFR-07).
- Минимальное покрытие тестами ключевых компонентов: карта с маршрутами, карточка объяснения, панель diff.

## 8. Критерии готовности (Definition of Done)

- [ ] Сценарий из раздела 2 полностью проходим в интерфейсе без обращения к API-клиенту вручную.
- [ ] На карте одновременно видны все заявки и маршруты всех бригад, различимые по цвету.
- [ ] Неназначенные заявки визуально отличимы (например, маркер другого цвета) и кликабельны для просмотра причины.
- [ ] Объяснение назначения открывается по клику на заявку и написано простым языком.
- [ ] После перепланирования интерфейс явно показывает, какие заявки/маршруты изменились, а какие остались прежними.
- [ ] Панель метрик показывает обе обязательные метрики и их значения для baseline рядом, плюс метрику простоя бригады (без сравнения с baseline — она не оптимизируется).
- [ ] Интерфейс корректно отображается на экране шириной 375px (мобильный) без горизонтального скролла основной разметки.
