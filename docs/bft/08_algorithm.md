# Алгоритм планирования маршрутов

Задача хакатона решается как статическая: тестовый набор заявок и бригад дан целиком (ТЗ п.2.1.1), и это соответствует моменту «планирование на завтра» из условия §43 — набор заявок на целевой день уже сформирован. Обязательная динамика ограничена одним событием перепланирования (ТЗ п.2.1.6). Раздел 5 показывает, что механизм этого события обобщается на реальный процесс накопления заявок (условие §43) и почему это не отменяет необходимости статической оптимизации, а объясняет её корректность.

## 1. Постановка задачи и её место в литературе

Задача одновременно требует четырёх свойств, и для каждого в литературе есть устоявшееся название:

| Свойство задачи | Источник требования | Академический термин |
|---|---|---|
| Бригада допустима для заявки только при совпадении навыка/транспорта (жёстко) | BR-06–BR-08 | **Site-Dependent VRP / Skill VRP** — Cappanera, Gouveia, Scutellà, *"The Skill Vehicle Routing Problem,"* INOC 2011, LNCS vol. 6701, pp. 354–364 |
| Жёсткие временные окна, обещанные клиенту | BR-20 | Классический **VRPTW** — Solomon (1987) |
| Целевая функция — сначала минимум бригад, потом минимум пробега | `01_business_requirements.md` §3, условие §22 | Тот же порядок, что и в оригинальных бенчмарках Solomon (1987) — иерархическая цель «число ТС → суммарное расстояние», канонический для VRPTW с 1987 года |
| Не все заявки обязаны быть выполнены — низкоприоритетную можно оставить без назначения с указанием причины | ТЗ п.2.2, п.2.3 | **Team Orienteering Problem with Time Windows (TOPTW)** — Vansteenwegen, Souffriau, Van Oudheusden, *"The orienteering problem: A survey,"* EJOR 209(1):1–10 (2011); обзор — Shena, Zhou, Lei, Wu, arXiv:2512.16865 (2025) |
| Зонтичный термин для задачи целиком (навыки + окна + маршруты техников) | — | **Technician Routing and Scheduling Problem (TRSP)** — Gamst et al., *"Decision support for the technician routing and scheduling problem,"* Networks, Wiley (2024) / arXiv:2211.16968; шире — **Workforce Scheduling and Routing Problem (WSRP)**, обзор Computers & Operations Research, DOI 10.1016/j.cor.2025.107344 (2025/2026) |

Задача — **Skill-VRPTW с приоритетно-взвешенным частичным покрытием и иерархической целью «сначала флот, потом расстояние»** (Site-Dependent VRPTW + TOPTW поверх иерархии Solomon). Эта комбинация целиком в готовом инструментарии не встречается (раздел 2).

Методологическая опора для конструктивных эвристик и метаэвристик VRPTW: Bräysy & Gendreau, *"Vehicle Routing Problem with Time Windows,"* Part I и Part II, Transportation Science 39(1), pp. 104–118 и 119–139 (2005); Ropke & Pisinger, *"An Adaptive Large Neighborhood Search Heuristic for the Pickup and Delivery Problem with Time Windows,"* Transportation Science 40(4):455–472 (2006) — источник ALNS, на нём основан пакет `alns` (раздел 2).

Ни один из проверенных open-source пакетов не покрывает все 4 свойства одновременно без ручной доработки или дополнительного сервиса. VROOM не даёт минимизацию флота как декларативную цель. PyVRP поддерживает жёсткие навыки только в платной Enterprise-версии — платный закрытый компонент не рассматривается как опция независимо от возможностей: это противоречит воспроизводимости решения по README (NFR-03) и не соответствует духу критерия «Подход команды» (понимание задачи и логики решения, а не готовое стороннее решение). jsprit решает навыки нативнее ценой отдельного JVM-сервиса на хакатон-стенде.

**Решение:** кастомная модель на **OR-Tools RoutingModel** — единственный вариант, покрывающий все 4 свойства без дополнительного сервиса и без лицензионных рисков (модель — [`05_spec_backend.md` §5](05_spec_backend.md#5-алгоритм-построения-плана-or-tools-routingmodel)). OR-Tools — конструктор примитивов (dimensions, disjunctions, allowed-vehicles, fixed costs), а не готовый пакет «Skill-VRPTW-TOPTW из коробки»: сопоставление навык→допустимые бригады, шкала штрафов по приоритету и трёхфазная оптимизация (раздел 4.1) собираются поверх этих примитивов под конкретные бизнес-правила задачи.

jsprit и `alns` остаются документированными резервными вариантами: jsprit — если декларативность skills-модели важнее деплоя второго сервиса; `alns` — если ограничения OR-Tools окажутся слишком жёсткими при реализации приоритетного вытеснения (BR-13); VROOM — при отказе от минимизации флота как отдельной декларативной цели.

**Baseline-алгоритм** (обязателен по ТЗ п.2.3 для сравнения) — последовательный проход по заявкам в порядке поступления, назначение первому подходящему по порядку исполнителю без глобальной оптимизации порядка посещения.

## 3. Что собирается из готовых примитивов, а что спроектировано под задачу

Прямое использование API OR-Tools (`SetAllowedVehiclesForIndex` для навыка/транспорта, `AddDisjunction` для допустимости отказа, dimension для временного окна) — конфигурация задокументированных функций. Поверх неё задача требует логики, которой в OR-Tools нет:

**Гарантия иерархии целей.** Единственный прогон солвера с доминирующим весом за бригаду — лишь приближение к иерархии «сначала флот, потом расстояние»: минимизация флота — отдельная, самостоятельно исследуемая в VRP-литературе подзадача, не гарантированный побочный эффект одного solve. Гарантирует иерархию только ступенчатая (лексикографическая) оптимизация — три последовательных прогона с сужающимися ограничениями (раздел 4.1).

**Атрибуция причины отказа.** Указать диспетчеру не просто «заявка не назначена», а конкретное решающее ограничение, требует последовательной процедуры проверки по группам ограничений (раздел 4.2), а не чтения первого сработавшего флага солвера.

**Постановка задачи и выбор инструмента.** Классификация задачи как Skill VRP + TOPTW + иерархия Solomon (раздел 1) и явный сравнительный анализ инструментов (раздел 2) предшествуют выбору OR-Tools, а не следуют из него.

**Протокол обработки события перепланирования** (раздел 5) — отдельно спроектированный механизм (Contract Net), не входящий в OR-Tools; тот же механизм, обобщённый, объясняет процесс накопления заявок на день (условие §43, раздел 5.4) без отдельной архитектуры под него.

## 4. Статический алгоритм

### 4.1. Ступенчатая (лексикографическая) оптимизация

Метод — преемптивное (лексикографическое) целевое программирование: Charnes & Cooper, *Management Models and Industrial Applications of Linear Programming*, Wiley (1961); связанный ε-constraint метод — Haimes, Lasdon, Wismer, *"On a bicriterion formulation of the problems of integrated system identification and system optimization,"* IEEE Trans. Systems, Man, and Cybernetics, SMC-1(3):296–297 (1971). Применительно к VRP с той же иерархией целей (сначала минимум ТС, потом минимум пробега) — Shi, Zhou, Boudouh et al., *"A lexicographic-based two-stage algorithm for vehicle routing problem with simultaneous pickup–delivery and time window,"* Engineering Applications of Artificial Intelligence, vol. 95 (2020): двухэтапный алгоритм вместо одной взвешенной целевой функции. Для выездных техников конкретно — Bangerter, Schindl, Pacheco Paneque, Tellache, Griset, *"A column-generation approach for an electricity technician routing and scheduling problem with a lexicographic objective,"* arXiv:2604.05153 (2026).

Три последовательных прогона солвера вместо одной целевой функции с весами; каждый следующий ограничен результатом предыдущего:

```
# Фаза 1 — максимум покрытия (цель №1)
solve_1 = solve(tickets, engineers, matrix,
                objective = minimize(Σ priority_weight[t] for t in unassigned))
C* = solve_1.covered_priority_weighted_score

# Фаза 2 — минимум бригад (цель №2), не хуже покрытия из фазы 1
solve_2 = solve(tickets, engineers, matrix,
                constraint = covered_priority_weighted_score >= C* - tolerance,
                objective = minimize(Σ SetFixedCostOfVehicle for used engineers))
K* = solve_2.engineers_used

# Фаза 3 — минимум пробега (цель №3), не хуже покрытия и флота из фаз 1–2
final_plan = solve(tickets, engineers, matrix,
                    constraint = covered_priority_weighted_score >= C* - tolerance,
                    constraint = engineers_used <= K*,
                    objective = minimize(Σ travel_time))
```

Каждая фаза использует тот же RoutingModel (навыки/окна/транспорт из раздела 4.3 не меняются между фазами) — меняется только целевая функция и добавляется ограничение по результату предыдущей фазы. Time-budget на фазу — доля общего лимита (NFR-02); если фаза не успевает найти доказанный оптимум, берётся лучшее найденное Guided Local Search решение (ТЗ п.2.3 не требует доказывать математический оптимум), допуск `tolerance` компенсирует это на границе между фазами.

Однопроходный вариант с доминирующим `SetFixedCostOfVehicle` — упрощение на случай дефицита времени при реализации; даёт только приближение к иерархии, не гарантию.

### 4.2. Атрибуция причины отказа

Для каждой неназначенной заявки — последовательная проверка по группам ограничений; берётся первая группа, на которой не осталось ни одного кандидата:

```
candidates = all_engineers_in_region
step1 = [e for e in candidates if required_skill in e.skills]
if not step1: return "no_skill"

step2 = [e for e in step1 if required_vehicle is None or e.vehicle_type == required_vehicle]
if not step2: return "no_vehicle"

step3 = [e for e in step2 if fits_in_shift_ignoring_current_route(e, ticket)]   # чистая проверка окна/смены
if not step3: return "shift_overflow"  # или no_time_slot, в зависимости от того, что нарушено

# Шаг 4 выполняется, только если реализована доп. возможность FR-20 (BR-11);
# в обязательном MVP оборудование не моделируется, шаг пропускается (step4 = step3).
step4 = [e for e in step3 if has_required_equipment(e, ticket)] if equipment_tracking_enabled else step3
if not step4: return "no_equipment"

# Технически подходящие есть, но все заняты другими заявками в это же время:
return "all_eligible_engineers_booked_elsewhere"
```

Последний случай реален и частый (несколько заявок с пересекающимися окнами при ограниченном числе квалифицированных бригад — прямо требуется тестовым набором по ТЗ п.6); код `all_eligible_engineers_booked_elsewhere` заведён в справочнике `UnassignedReason` (`05_spec_backend.md` §2) отдельно от `no_time_slot`.

### 4.3. Сборка модели

Полная модель — [`05_spec_backend.md` §5](05_spec_backend.md#5-алгоритм-построения-плана-or-tools-routingmodel).

```
1. Узлы = депо бригады (старт) + все заявки региона на целевой день.
2. Матрица времени — OSRM по графу дорог, отдельно по профилю транспорта (BR-09, BR-10).
3. Жёсткая допустимость узла для бригады = совпадение навыка (BR-06/07) И совпадение
   требуемого транспорта, если задан (BR-08)               → Skill VRP (раздел 1)
4. Жёсткое временное окно на узел-заявку (BR-20)            → VRPTW
5. AddDisjunction на каждый узел-заявку со штрафом,
   пропорциональным приоритету (Авария ≫ Подключение ≫ Ремонт/Дозаказ, BR-12)
                                                              → TOPTW (частичное покрытие)
6. Три фазы раздела 4.1 вместо одной целевой функции          → гарантирует иерархию Solomon (1987)
7. Guided Local Search (встроенная метаэвристика OR-Tools) ищет решение в отведённое время каждой фазы.
8. Атрибуция причины отказа — раздел 4.2; для назначенных — текст из значений
   (allowed vehicles, dimension slack), которые солвер использовал на шагах 3–5.
```

## 5. Событие перепланирования (FR-13)

MVP требует обработать одно событие из трёх: новая срочная заявка, отмена заявки, недоступность бригады (ТЗ п.2.1.6). Повторный вызов солвера раздела 4 на всех данных дня для одного события избыточен и противоречит BR-17 (минимальное изменение уже согласованного плана).

### 5.1. Механизм (Contract Net Protocol, Smith 1980)

```
1. Диспетчер формирует «задание»: событие (тикет/бригада) → рассылка бригадам-кандидатам региона,
   допустимым по навыку/транспорту (шаг 3 раздела 4.3).
2. Каждая бригада-кандидат считает свою «ставку» — доп. время при вставке заявки в свой
   текущий маршрут в лучшей допустимой позиции (без нарушения уже стоящих окон, BR-19/BR-20).
3. Побеждает бригада с минимальной ставкой; план обновляется точечно, формируется diff.
```

### 5.2. Приоритетное вытеснение (авария, BR-13)

Если ни одна бригада не может вставить аварийную заявку без нарушения чужих окон — заявка с более низким приоритетом в маршруте наиболее подходящей бригады сама становится новым «заданием» и повторно торгуется среди остальных бригад. Глубина каскада ограничена одним уровнем: неограниченная рекурсия свела бы «минимальное изменение» к пересчёту всего дня, что противоречит цели BR-17.

### 5.3. Почему не отдельный вызов солвера

`PlanStability` получается по построению — число бригад, чей маршрут реально задет протоколом, без отдельного diff-алгоритма поверх двух независимо посчитанных планов. Каждая бригада пересчитывает только свой собственный маршрут (BR-01: бригада = агент).

### 5.4. Обобщение на процесс накопления заявок (условие §43)

Условие §43 (*«Постановка слотов для назначения заявок - месяц вперед. Планирование на завтра»*) означает, что заявки на день в реальности накапливаются постепенно: клиент звонит, ему предлагают доступные окна на выбранный день, он выбирает одно. Это тот же протокол из 5.1, применяемый непрерывно:

- «Задание» — любая новая заявка, не только авария/отмена/недоступность.
- «Ставка» бригады — проверка, войдёт ли заявка в её уже существующий на этот день маршрут без нарушения обещанных окон.
- Клиенту показываются только те временные окна, для которых нашлась хотя бы одна допустимая бригада.
- Новая бригада активируется только когда ни одна уже активная не прошла проверку.

```
def offer_slots(new_ticket, active_brigades, idle_brigades_pool):
    candidates = []
    for b in active_brigades:
        if eligible(b, new_ticket):
            for slot in feasible_insertion_slots(b.route, new_ticket):
                # feasible = не нарушает окна new_ticket И не нарушает уже обещанные окна
                # других заявок в маршруте b (BR-20 — обещание неприкосновенно)
                candidates.append((b, slot, marginal_cost(b, slot, new_ticket)))
    if not candidates:
        for b in idle_brigades_pool:
            if eligible(b, new_ticket):
                for slot in feasible_insertion_slots(b.empty_route, new_ticket):
                    candidates.append((b, slot, marginal_cost(b, slot, new_ticket) + activation_penalty))
    return sorted(candidates, key=cost)   # → список тайм-слотов, показываемый клиенту

def commit(new_ticket, chosen_slot):
    insert(new_ticket, chosen_slot)       # окно клиенту обещано — далее неприкосновенно (BR-20)
```

Научная база: Agatz, Campbell, Fleischmann, Savelsbergh, *"Time Slot Management in Attended Home Delivery,"* Transportation Science 45(3):435–449 (2011); *"Managing Concurrent Interactions in Online Time Slot Booking Systems for Attended Home Delivery,"* Transportation Science, DOI 10.1287/trsc.2022.0445 (2022–2023); Demiray, Tolga, Yücel, *"An Optimization Framework for a Dynamic Multi-Skill Workforce Scheduling and Routing Problem with Time Windows and Synchronization Constraints,"* arXiv:2309.09321 (2023) — мультинавыковые выездные бригады, временные окна, динамическое перепланирование по приходу новой задачи, решение через ALNS. Терминология паттерна «онлайн-вставка + периодическая пакетная переоптимизация» — из таксономии обзоров Dynamic VRP: Pillac, Gendreau, Guéret, Medaglia, EJOR 225(1):1–11 (2013); Psaraftis, Wen, Kontovas, *"Dynamic Vehicle Routing Problems: Three Decades and Counting,"* Networks 67(1):3–31 (2016). Проверка допустимости вставки новой заявки в уже закреплённые маршруты без нарушения чужих обещаний — Ichoua, Gendreau, Potvin, *"Diversion Issues in Real-Time Vehicle Dispatching,"* Transportation Science 34(4):426–438 (2000).

### 5.5. Почему статическая пакетная оптимизация остаётся необходимой

Задача структурно — online bin packing (бины — бригады): жадное онлайн-размещение объектов, прибывающих по одному, доказанно хуже офлайн-оптимума в худшем случае. First-Fit для online bin packing использует не более ≈1.7×OPT + 2 бинов (Johnson, *"Fast Algorithms for Bin Packing,"* J. Comput. Syst. Sci. 8(3):272–314, 1974; детальные границы — Johnson, Demers, Ullman, Garey, Graham, *"Worst-Case Performance Bounds for Simple One-Dimensional Packing Algorithms,"* SIAM J. Computing 3(4):256–278, 1974). Даже онлайн-слой с проверкой допустимости (не наивный FCFS) в худшем случае использует заметно больше бригад, чем необходимо. Статическая оптимизация (раздел 4.1) закрывает этот разрыв: не трогает уже обещанные клиентам окна (BR-20), но пересматривает, какая бригада едет к каждому клиенту (условие §20: «Назначенные заявки можно менять») — то есть перекладывает уже принятые заявки между бригадами до настоящего минимума флота, а не его онлайн-приближения.

### 5.6. Объём реализации

Тестовый набор хакатона — готовый CSV/JSON (ТЗ п.2.1.1), то есть уже состояние «на закрытие» процесса накопления заявок (условие §43). В реализацию идёт: статический 3-фазный Skill-VRPTW solve (раздел 4) как основной путь, baseline FCFS (`05_spec_backend.md` §7), атрибуция причины отказа (§4.2), одно обязательное событие перепланирования (§5.1–5.2) как частный вызов протокола раздела 5.4. Полный online-слой бронирования (§5.4) в демо-сценарий ТЗ (раздел 4 ТЗ, управляется загружаемым набором) не входит и остаётся доп. возможностью (раздел 6) — код для него совпадает с кодом обязательного события, поэтому реализуется как расширение, а не отдельная подсистема.

def build_baseline_plan(region, tickets, engineers) -> Plan:

def replan(plan: Plan, event: ReplanEvent) -> Plan:           # §5 — обязательный минимум: 1 событие
    if event.type == "new_urgent_ticket":
        winner, bids = contract_net_announce(plan, event.ticket)     # §5.1
        if winner is None and event.ticket.priority == "urgent":
            winner = eviction_procedure(plan, event.ticket, max_depth=1)  # §5.2
        plan = apply_insertion(plan, event.ticket, winner)
    elif event.type == "ticket_cancelled":
        plan = remove_ticket(plan, event.ticket_id)
    elif event.type == "engineer_unavailable":
        for ticket in plan.tickets_of(event.engineer_id, not_started=True):
            winner, _ = contract_net_announce(plan, ticket, exclude=event.engineer_id)
            plan = apply_insertion(plan, ticket, winner) if winner else mark_unassigned(plan, ticket)
    return with_diff(plan, previous=plan.parent)
