Основан на фактическом просмотре `docs/synthetic_data/*.csv`, `docs/control_distribution/*.csv` и `docs/Нормативы.xlsx`. Кодировка исходных CSV — **Windows-1251**, разделитель — `;`. При импорте это нужно учитывать (`encoding='cp1251'`), иначе поля будут читаться как «кракозябры».

Контрольные значения — ориентир по числу бригад (условие §37–38), не эталон для повторения (BR-29, условие §2).

> **Число заявок считается по фактическим строкам-заявкам, не по числу строк в файле.** В каждом файле синтетических данных после последней заявки идут 2 пустые строки и одна служебная строка-сентинел с адресом офиса региона: значение `Заявка` = `Адрес Офиса` (Восток, Юго-Восток; с заглавной «О») либо `Адрес офиса` (Югоцентр; со строчной «о» — регистр не унифицирован между файлами), а сам адрес офиса лежит во втором столбце (`Тип заявки BK`) вместо ожидаемого типа заявки. Итого «сырых» строк данных в файле на 3 больше числа реальных заявок (69/86/59 против 66/83/56 выше). Загрузчик должен явно отфильтровывать пустые строки и строку `Заявка ∈ {"Адрес Офиса", "Адрес офиса"}` **до** валидации обязательных полей заявки — иначе она либо провалит валидацию как невалидная заявка, либо (при мягкой валидации) попадёт в план как заявка-мусор. Эта же строка — единственный источник адреса офиса, требуемого BR-02/условием №4 в качестве стартовой точки бригад региона.

Районы (`Район`), встречающиеся в данных, — используются как есть для геокодирования/подсказки координат, если явные координаты не заданы:

- **Юго-Восток:** Бирюлево Восточное, Бирюлево Западное, Братеево, Домодедово, Зябликово, Кашира, Москворечье-Сабурово, Орехово-Борисово Северное, Орехово-Борисово Южное, Ступино, Царицыно.
- **Югоцентр:** Академический, Гагаринский, Даниловский (в т.ч. «GPON Даниловский»), Донской, Замоскворечье, Зюзино, Котловка, Нагатино-Садовники, Нагатинский Затон, Нагорный, Хамовники.

> Кашира, Ступино, Домодедово — удалённые города Подмосковья: стартовая точка бригады для них задаётся самостоятельно как условная точка «дома» в городе, без реальных GPS-координат (BR-02, условие §39).

## 2. Структура файла синтетических данных (заявки)

| Колонка (как в CSV) | Тип/формат | Комментарий |
|---|---|---|
| `Заявка` | integer | Внешний идентификатор заявки |
| `Тип заявки BK` | string, enum | Фактические значения в данных: `Подключение`, `Дозаказ`, `Локальная заявка`, `Глобальная проблема`. Значение `Авария` в этой колонке **не встречается** ни в одном из шести файлов (синтетика + контроль) — авария в данных закодирована как `Тип заявки BK = Глобальная проблема` + `Тип заявки HD = Авария` (см. раздел 3) |
| `Тип заявки HD` | string, enum | См. раздел 3 — детальный список и маппинг в `Skill` |
| `Начало` / `Окончание` | `DD.MM.YYYY HH:MM` | Временное окно, обещанное клиенту (BR-20); в примерах дата фиксирована — `17.08.2026` |
| `Район` | string | См. раздел 1 |
| `Адрес` | string | Полный адрес; для геокодирования (координаты не заданы явно в исходных данных — синтезируются/геокодируются командой) |
| `Подключение` | string, enum | Только в файле региона «Восток»: `FMC`, `FTTB` — технология подключения, не тип транспорта |
| `Гигабитное подключение` | `Да` / `Нет` | Признак повышенных технических требований к заявке подключения |

> В файлах «Юго-Восток» и «Югоцентр» колонка `Подключение` отсутствует — учитывать вариативность состава колонок между регионами при разработке загрузчика (не полагаться на фиксированный набор столбцов, определять по заголовку).

## 3. Тип заявки HD → требуемый навык (маппинг, BR-27)

`Тип заявки ВК` (Beekeeper) и `Тип заявки HD` (HelpDesk) — обозначения одной и той же заявки в разных системах, не два вида работ (условие §32). Значения `Тип заявки HD`, встреченные в данных, и предлагаемое соответствие справочнику навыков (`Skill`, ТЗ п.2.4.1):

| `Тип заявки HD` (фактическое значение в данных) | `Тип заявки BK` (фактически наблюдаемый в паре) | Предлагаемый `required_skill` |
|---|---|---|
| Авария | Глобальная проблема | `emergency` |
| Заявка на подключение | Подключение | `connection` |
| Конвергенция абонента | Подключение | `connection` |
| Заказ подключения/Дозаказ оборудования | Подключение / Дозаказ | `connection` |
| Дозаказ оборудования | Дозаказ | `connection` |
| Переключение на Гбит/с | Локальная заявка | `local_work` |
| Роутер. Замена техническим специалистом | Локальная заявка | `local_work` |
| TVE/ENT. Замена приставки техником | Локальная заявка | `local_work` |
| ТВ. Замена приставки техником | Локальная заявка | `local_work` |
| Работа с кабелем | Локальная заявка | `local_work` |
| Нет линка | Локальная заявка | `local_work` |
| Низкая скорость | Локальная заявка | `local_work` |
| Рост ошибок на порту | Локальная заявка | `local_work` |
| Разрывы | Локальная заявка | `local_work` |
| Мониторинг | Локальная заявка | `local_work` |
| Информация | Глобальная проблема | `local_work` |
| IP-адрес 169... | Локальная заявка | `local_work` |
| TVE/ENT. Другие ошибки | Локальная заявка | `local_work` |

Правило приоритета маппинга (**исправлено по факту разбора всех шести файлов** — исходная формулировка «`Тип заявки BK = Авария`» была неверна: такого значения в колонке BK не существует ни в одном файле): **`Тип заявки HD = Авария` всегда даёт `required_skill = emergency`**, независимо от значения BK (в данных этому HD-значению всегда сопутствует `BK = Глобальная проблема`, но правило проверяется по HD, а не по BK — BK=«Глобальная проблема» без HD=«Авария» уходит в `local_work`, см. строку «Информация» выше); для остальных HD-значений маппинг — по таблице выше. `ТВ.` и `TVE/ENT.` — это два разных литеральных значения HD в данных (не варианты записи одного и того же), обе строки нужны в конфигурации отдельно. Таблица должна быть вынесена в конфигурацию (не хардкод в коде), чтобы её было легко скорректировать по факту полного набора значений.

> **Важно:** в файле «Югоцентр» (синтетика и контроль) `HD = Авария` не встречается ни разу — в этом региональном сценарии нет ни одной аварийной заявки. Если Югоцентр используется для демонстрации логики приоритетного вытеснения аварией (BR-12–BR-14, FR-14), команда обязана синтезировать хотя бы одну аварийную заявку для этого региона самостоятельно и явно задокументировать это как допущение (BR-28) — в исходных данных её взять неоткуда.

## 5. Нормативы длительности работ (`docs/Нормативы.xlsx`, минуты)

| Название работы | Дорога до клиента/ТКД | Технические работы | Документы | Базовый норматив (итого) |
|---|---|---|---|---|
| Подключение клиентов (базовая) | 20 | 60 | 10 | 90 |
| Авария на ТКД | 20 | 80 | 0 | **100** |
| Дозаказ оборудования | 20 | 10 | 10 | 40 |
| Локальная заявка/ремонт у клиента | 20 | 30 | 0 | 50 |

Правило использования в модели (см. `05_spec_backend.md` раздел 8): в расписание заявки закладывается длительность **«Технические работы» + «Документы»** (время непосредственно на объекте) — для всех типов заявок это правило не меняется, `duration_min` везде равен этой сумме.

Компонент «Дорога до клиента/ТКД» трактуется по-разному в зависимости от типа заявки:
- **Подключение, Дозаказ, Локальная заявка** — справочный норматив, не замена расчёта времени в пути по графу дорог, который выполняется отдельно через OSRM для каждой пары точек (BR-10); это разделение остаётся допущением команды, задокументированным в README.
- **Авария** — по условию conditions.md **№45** дорога прямо входит в норматив выполнения (100 минут = 20 мин на дорогу до ТКД + 80 мин на объекте), это уже не допущение, а закреплённое организатором правило: 20-минутная составляющая норматива BR-14 фиксирована и не пересчитывается через OSRM, в отличие от фактического маршрута/пробега бригады до аварии, который по-прежнему строится через OSRM (BR-10) и входит в обязательные метрики плана.

Соответствие норматива и справочника заявок:

| Тип работы (логический, после маппинга раздела 3) | Норматив | `duration_min` (на объекте) |
|---|---|---|
| Подключение (`BK = Подключение`) | Подключение клиентов Базовая | 70 (60+10) |
| Авария (`BK = Глобальная проблема` + `HD = Авария`, см. раздел 3 — **не** `BK = Авария`, такого значения в данных нет) | Авария на ТКД | 80 (только тех. работы; общий норматив выполнения — 100 мин., фиксированно 20 мин на дорогу до ТКД + 80 мин на объекте по условию conditions.md №45, BR-14 — не переменное OSRM-время) |
| Дозаказ (`BK = Дозаказ`) | Дозаказ оборудования | 20 (10+10) |
| Локальная заявка / прочая «Глобальная проблема» (`BK = Локальная заявка` либо `BK = Глобальная проблема` без `HD = Авария`) | Локальная заявка/ремонт у клиента | 30 |

## 6. Значения дополнительных полей заявки

- `Подключение` (только регион «Восток»): `FMC` (Fixed Mobile Convergence), `FTTB` (Fiber To The Building) — технология подключения, влияет на техническую сложность, не используется как навык или транспорт.
- `Гигабитное подключение`: `Да`/`Нет` — признак повышенных требований к оборудованию/навыку монтажника; при `Да` — рекомендуется требовать более высокий уровень квалификации/отдельный вид оборудования, если команда вводит уровни квалификации (условие §36).

## 8. Архив пробок Яндекса (`docs/ymarchive`) — опциональный источник калибровки скорости

Разрешён к использованию наравне с остальными данными. Внутри:

| Файл | Содержимое | Использовать? |
|---|---|---|
| `2015-12-01-ymarchive.zip` → `ymsave.sql` (~1.1 МБ) | MySQL-дамп, таблица `hours(hour, minute, traf, temp, damp)` — **общегородской** почасовой балл пробок Москвы (шкала Яндекса 0–10), температура, осадки; данные с сентября 2013 г. | Да — компактно, легко распарсить в Python (regex/`sqlparse` по INSERT-строкам или временный импорт в PostgreSQL) |
| `2015-12-01-ymarchive.zip` → `rp5.csv` (~6.2 МБ) | Почасовая погода с rp5.ru за тот же период | Опционально, как источник температуры/осадков, если понадобится для объяснений/прогноза |
| `2015-12-01-ymarchive-maps.zip.001…006` (~1.2 ГБ суммарно) | Судя по названию и объёму — скриншоты карт пробок (визуальный слой веб-приложения из архива), не структурированные данные по сегментам дорог | **Не рекомендуется** распаковывать/парсить для MVP: несоразмерно тяжело относительно пользы, нет очевидного машиночитаемого формата сегментов дорог |

**Как встроить в модель (доп. возможность, не MVP):** таблица `hours` даёт общегородской индекс загруженности по часам, а не скорость на конкретном ребре графа. Практическое применение — калибровочный коэффициент замедления для профиля `car` в OSRM по часу дня: для планируемой даты подобрать аналогичный исторический день (тот же день недели/месяц) и взять усреднённый `traf` по часам как множитель к времени в пути автомобилиста. Это усиливает реализм условия §19 (скорость важнее прямого расстояния и зависит от транспорта), но не заменяет обязательный расчёт по графу дорог (BR-10) и не входит в обязательный MVP — ни ТЗ, ни `conditions.md` не требуют трафик-модели явно.

## 9. Известные особенности исходных CSV, важные для парсера

- Кодировка **Windows-1251** (не UTF-8) — обязательна явная конвертация при чтении.
- Набор колонок не идентичен между регионами (пример: `Подключение` есть только у «Восток») — загрузчик должен определять поля по заголовку, а не по фиксированной позиции.
- В адресах встречаются `;`-подобные визуальные разделители внутри значения (запятые, номера корпусов/строений) — при парсинге стандартным CSV-ридером (не построчным split) риска разрыва поля нет, но при самостоятельной генерации тестов нужно проверять на реальных строках, а не только на «чистых» примерах.
- Даты во всех примерах — на 2026 год (синтетический сдвиг), единый день `17.08.2026`; часовой пояс — Москва (BR-21).
