# Техническое задание — Backend

Ссылки: бизнес-требования — [`01_business_requirements.md`](01_business_requirements.md), стек — [`02_tech_stack.md`](02_tech_stack.md), точная спецификация API/модели — [`05_spec_backend.md`](05_spec_backend.md).

## 1. Цель модуля

Реализовать сервис, который: принимает данные о заявках и бригадах, строит план распределения и маршрутов на день с соблюдением обязательных ограничений, отдаёт объяснения по каждому назначению/отказу, считает обязательные метрики, сравнивает с базовым алгоритмом и пересобирает план по событию перепланирования с минимальными изменениями.

## 2. Состав функциональности (обязательный MVP)

1. **Загрузка данных.** Импорт заявок из CSV/JSON (формат ТЗ п.2.4) либо использование встроенного демо-набора на основе `docs/synthetic_data`; бригады региона создаёт детерминированный генератор демо-бригад. Реализовать: FR-01, FR-02, FR-03, FR-04.
2. **Матрица времени в пути.** Для набора точек (старты бригад + адреса заявок) построить матрицу «время в пути / расстояние» по дорожной сети через OSRM, отдельно по каждому типу транспорта, присутствующему в наборе бригад. Реализовать: FR-07.
3. **Построение плана (Skill-VRPTW, три фазы).** На вход — заявки (координаты/адрес, окно, длительность, приоритет, требуемый навык, требуемый транспорт), бригады (старт, смена, навыки, транспорт, при включённом расширении — оборудование). Решается **тремя последовательными фазами** (максимум покрытия → минимум бригад при этом покрытии → минимум пробега при этом флоте), а не одним вызовом солвера с весами — иначе иерархия целей из условия §22 не гарантирована, а только приближена; полная процедура — [`08_algorithm.md` §4.1](08_algorithm.md#41-ступенчатая-лексикографическая-оптимизация). На выходе — назначение заявка→бригада, порядок посещения, плановое время прибытия, для неназначенных — код и текст причины. Реализовать: FR-05, FR-06, FR-10, FR-14, FR-17, FR-18, FR-19.
4. **Baseline-алгоритм.** Отдельная простая реализация «первая подходящая бригада по порядку поступления заявок», без глобальной оптимизации порядка посещения — для контрольного сравнения метрик. Реализовать: FR-12.
5. **Метрики.** Число уникальных задействованных бригад; пробег/время по каждой бригаде и суммарно; сравнение метрик «основной план vs baseline». Реализовать: FR-11, FR-12.
6. **Объяснения (explainability).** Для каждой назначенной заявки — текстовое объяснение (какая бригада, почему именно она, какие ограничения учтены). Для каждой неназначенной — причина, определённая **последовательной процедурой атрибуции по группам ограничений** (не первым проваленным чек-флагом), из фиксированного набора кодов: нет навыка / нет свободного времени в окне / нет нужного транспорта / не помещается в смену / нет оборудования (код активен только при реализации доп. возможности FR-20, см. BR-11) / все технически подходящие бригады заняты другими заявками — процедура и обоснование шестого кода — [`08_algorithm.md` §4.2](08_algorithm.md#42-атрибуция-причины-отказа). Реализовать: FR-15.
7. **Перепланирование.** Обработка одного события: новая срочная (аварийная) заявка, отмена заявки, недоступность бригады. Требования: приоритет аварии может вытеснять уже назначенные заявки бригады без нарушения их временных окон (BR-13), но не прерывает начатую работу (BR-32); бригада для аварии выбирается по её состоянию на момент события и целевому времени реакции 1–2 часа (BR-33); изменения должны быть минимальны относительно предыдущего плана (BR-17); ответ должен явно перечислять, что изменилось (diff). Механизм — Contract Net протокол между бригадами-агентами, а не повторный вызов глобального солвера; полное описание — [`08_algorithm.md`](08_algorithm.md#5-событие-перепланирования-fr-13). Реализовать: FR-13, FR-16.
8. **Жизненный цикл статусов заявки.** Хранение и переходы статусов (`Отправлена → В пути → В работе → Завершено`, либо `Отменена`, либо `Просрочена`); закрытые заявки исключаются из последующего перепланирования. Реализовать: FR-28.
9. **Время без временной зоны.** Все внутренние расчёты и хранение времени — в наивном представлении (без tz), в поясе региона; конвертаций в UTC/серверный пояс не вводится (условие §17). Реализовать: FR-29.
10. **Метрика простоя бригады.** Считается и отдаётся в ответе API как справочное значение, не участвует ни в целевой функции солвера, ни в сравнении с baseline (условие §42). Реализовать: FR-23.
11. **REST API** для фронтенда с OpenAPI-документацией (автогенерация FastAPI).

## 3. Дополнительные возможности (не блокируют сдачу MVP)

- Учёт оборудования при назначении (FR-20).
- Метрики балансировки загрузки и стабильности плана (FR-21, FR-22).
- Ручное переназначение поверх автоплана (FR-24).
- Несколько последовательных сценариев перепланирования за сессию (FR-25).
- Вставка новой обычной заявки в течение дня в свободный интервал бригады без перестройки плана — событие `new_ticket` (FR-34, BR-31).
- Эксперимент с гибкими временными окнами (FR-33).
- Прогноз риска нарушения SLA/опоздания (FR-26).
- Комбинированные маршруты с общественным транспортом (FR-27).
- Динамическое перепланирование как расширяемая возможность поверх статического MVP-плана — несколько последовательных событий за день, а не одно обязательное (FR-32; `01_business_requirements.md` §7 относит его к дополнительным возможностям, не к обязательному MVP).
- Биоинспирированная локальная доводка порядка остановок бригады поверх Contract Net-назначения (см. [`08_algorithm.md`](08_algorithm.md#6-необязательные-расширения)).

## 4. Бизнес-правила, обязательные к реализации в коде (не только в UI)

Прямая ссылка на разделы 4.1–4.5 `01_business_requirements.md`. Ключевые для backend-логики:

- Квалификация: назначение запрещено, если требуемый навык заявки отсутствует у бригады (BR-06, BR-07) — жёсткое ограничение солвера, не мягкий штраф.
- Транспорт: если заявка требует конкретный тип транспорта — назначение только бригаде с этим типом (BR-08) — жёсткое ограничение.
- Время: расчёт прибытия = текущее время + время в пути по графу дорог по профилю транспорта бригады; прибытие должно попасть в `[Начало, Окончание]` заявки; суммарная занятость бригады не должна выходить за пределы смены (BR-20, BR-09, BR-10, BR-19) — жёсткие ограничения.
- Приоритет: очередность вставки/вытеснения заявок при построении и при перепланировании — Авария → Подключение → Ремонт/Дозаказ (BR-12); аварийная заявка после появления получает норматив 100 минут и может вытеснить уже стоящие в графике заявки бригады, только если это не ломает их окна (BR-13, BR-14).
- Регион: заявки и бригады строго одного региона (одного CSV-файла) обрабатываются вместе; кросс-региональные назначения запрещены (BR-03). Внутри региона территория (Москва / удалённый город Подмосковья) назначение не ограничивает (BR-30).
- Норматив на дорогу (20 мин) — резерв при бронировании слота; в плане и при перепланировании время в пути всегда расчётное по графу дорог (BR-14).
- Часовой пояс: все внутренние расчёты времени — в наивном (без tz) представлении в поясе клиента/региона; конвертация — только на границе API (BR-21).

## 5. Нефункциональные требования к backend

- Время построения плана для ≤100 заявок / 10–15 бригад — не более нескольких секунд на ноутбуке участника (NFR-02).
- Все обязательные ограничения покрыты юнит-тестами (пример: назначение с недостающим навыком должно быть отклонено солвером и/или тестом) (NFR-06).
- Конфигурация окружения — через переменные окружения/`.env` (URL OSRM, путь к БД, режим demo/full).
- Логирование — структурированное (structlog: имя события + поля, JSON в `stdout`). Ключевые шаги — загрузка данных, построение плана, событие перепланирования — логируются с идентификатором запуска (`run_id`) для трассировки в объяснениях; каждая запись запроса несёт `request_id`, который возвращается клиенту в заголовке `X-Request-ID`.
- Ошибки логируются дважды по смыслу, а не дублем: бизнес-ошибка — в обработчике эндпоинта (что не удалось и с какими параметрами), ошибка БД или внешнего сервиса (OSRM, геокодер) — в месте возникновения с техническими деталями. Обе записи связаны общим `request_id`.
- Backend не хранит авторизационных данных, не требует аутентификации (NFR-04).

## 6. Интерфейс с фронтендом

- Транспорт — REST/JSON поверх HTTP, контракт — OpenAPI 3.1, пишется до кода (`specs/openapi.yaml` в корне репозитория; общие компоненты, включая схему ошибки, — `specs/common.yaml`). В спеке у каждого входного параметра строго заданы ограничения (длина строк, `pattern`, диапазоны чисел, размер массивов, `additionalProperties: false`): по ним проверяет ввод и backend (без кода проверки в обработчиках — через сгенерированные модели), и формы фронтенда.
- Полный перечень эндпоинтов, схем запросов/ответов — [`05_spec_backend.md`](05_spec_backend.md#4-api-контракт).
- Ошибки возвращаются одинаково для всех эндпоинтов ([`05_spec_backend.md` §4.5](05_spec_backend.md#45-ошибки)): тело есть только у `400` — текст ошибки или список «параметр + ошибка» для отображения на форме, в том числе ошибки валидации входных CSV/JSON; остальные коды ошибок возвращаются без тела, и текст для диспетчера фронтенд формирует по коду ответа.

## 7. Критерии готовности (Definition of Done)

- [ ] Загрузка демо-набора и произвольного CSV/JSON по формату ТЗ работает без ручных правок файла, включая корректную фильтрацию пустых строк и служебной строки-сентинела адреса офиса (`07_data_dictionary.md` §1).
- [ ] План строится с соблюдением 3 обязательных групп ограничений; при их нарушении в тестах — явный fail.
- [ ] Каждая неназначенная заявка имеет непустую, отличную от общей, причину, определённую процедурой атрибуции (`08_algorithm.md` §4.2), а не первой проваленной проверкой.
- [ ] Тест-кейс: на наборе с намеренным дефицитом квалифицированных бригад (несколько пересекающихся по времени заявок, ТЗ п.6) план, полученный тремя фазами (§4.1), использует не больше бригад, чем однопроходный вариант с весами, на тех же данных.
- [ ] Обязательные метрики считаются и совпадают по составу с ТЗ п.2.3.
- [ ] Baseline-план строится независимо от основного алгоритма и участвует в сравнении.
- [ ] Все datetime-значения в БД и в API — наивные (без tz), время трактуется в поясе региона; нет мест, где время неявно конвертируется через UTC/серверный часовой пояс.
- [ ] Метрика простоя бригады считается и возвращается в API, но не входит ни в целевую функцию солвера, ни в сравнение план/baseline.
- [ ] Одно из трёх событий перепланирования обрабатывается end-to-end с diff-ответом.
- [ ] Аварийная заявка, добавленная в течение дня, способна вытеснить ранее назначенную заявку без нарушения её окна — покрыто тестом.
- [ ] Заявка в статусе «В работе» при перепланировании по аварии остаётся за бригадой, бригада едет на аварию только после её завершения — покрыто тестом.
- [ ] OpenAPI-схема доступна и соответствует фактическим эндпоинтам.
