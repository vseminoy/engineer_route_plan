# Бизнес-функциональные требования

## 1. Контекст и цель

«Билайн Бизнес» ежедневно распределяет между выездными инженерами (бригадами) заявки на подключение, аварии, ремонт и дозаказ оборудования. Ручное распределение не позволяет одновременно учитывать квалификацию, доступный транспорт, временные окна, согласованные с клиентом, и оперативные изменения (аварии, отмены, недоступность бригады).

**Цель системы:** дать диспетчеру инструмент, который за минуты строит выполнимый план работы бригад на день, показывает его на карте, на понятном языке объясняет принятые решения и умеет пересобрать план при внештатном событии с минимальными изменениями уже согласованного расписания.

Система — прототип (MVP) для демонстрации на хакатоне, не промышленное решение: без авторизации, без микросервисной инфраструктуры, без отказоустойчивости уровня production (см. раздел 6).

## 2. Роли и участники

| Роль | Описание | Использует систему |
|---|---|---|
| **Диспетчер** | Основной пользователь. Запускает планирование, просматривает карту и маршруты, инициирует события перепланирования, читает объяснения, при необходимости переназначает заявки вручную. | Веб-интерфейс (десктоп/моб.) |
| **Бригада (инженер)** | Один человек = одна бригада ([BR-01](#41-организационные-правила)). Исполняет назначенные заявки, сообщает диспетчеру о выполнении/невозможности выполнения/отмене. В MVP не имеет собственного интерфейса — статусы вносит диспетчер от её имени. | Не взаимодействует с системой напрямую в MVP; целевой интерфейс адаптирован под мобильные устройства ([FR-31](#5-функциональные-требования)) для будущего мобильного клиента бригады |
| **Клиент** | Заказчик заявки. Согласовывает временное окно, может отменить заявку после назначения бригады. | Не взаимодействует с системой; коммуницирует через службу поддержки |
| **Служба поддержки** | Уведомляет клиента при сдвиге ранее согласованного времени в результате перепланирования. | Вне контура MVP; система должна явно фиксировать факт изменения, требующего уведомления |
| **Система (планировщик)** | Автоматически распределяет заявки, строит маршруты, пересчитывает план по событиям, формирует объяснения и метрики. | — |

## 3. Бизнес-цели и критерии успеха

Приоритет критериев качества плана (условие [#22](../conditions.md)), от главного к второстепенному:

1. **Максимум выполненных заявок** — минимум неназначенных.
2. **Минимум задействованных исполнителей** — меньше уникальных бригад с хотя бы одной заявкой.
3. **Оптимальность маршрута** — минимальный пробег/время в пути по каждой бригаде и суммарно.

Дополнительно (не влияют на основной критерий, но наблюдаются):

- балансировка загрузки бригад (`LoadBalance = StdDev(WorkingTime)`, макс./мин. загрузка, число переработок);
- стабильность плана при перепланировании (`PlanStability = NumberOfChangedAppointments`, минимально необходимое изменение вместо пересборки всего дня);
- простой бригады — метрика только для наблюдения, в оптимизации не участвует ([BR-19](#43-приоритизация-и-перепланирование)).

## 4. Бизнес-правила

Правила ниже — нормализованный свод условий [`conditions.md`](../conditions.md) и постановки задачи, обязателен для соблюдения алгоритмом и интерфейсом.

### 4.1. Организационные правила

- **BR-01.** Бригада = один человек (1:1).
- **BR-02.** Стартовая точка бригады — адрес офиса из синтетических данных; для удалённых городов Подмосковья (Кашира, Ступино, Домодедово и т.п.) — самостоятельно заданная условная точка «дома» бригады в этом городе, без реальных GPS.
- **BR-03.** Три региона синтетических данных (Восток, Юго-Восток, Югоцентр) — три независимых сценария; 1 регион = 1 CSV-файл (условие №46). Заявки разных регионов не пересекаются и не могут перераспределяться между бригадами разных регионов. Московские заявки и заявки удалённого Подмосковья из одного файла относятся к одному региону (см. BR-30).
- **BR-04.** Планирование выполняется в пределах одного рабочего дня. Постановка слотов заявок клиентам возможна на месяц вперёд, но алгоритм строит итоговый план «на завтра» — на конкретный целевой день, когда набор заявок по нему уже сформирован. Реализация получает этот набор как готовую выгрузку (ТЗ п.2.1.1) и решает статическую задачу — обоснование того, как реальный процесс поступления заявок соотносится со статическим решением — [`08_algorithm.md` §5](08_algorithm.md#5-событие-перепланирования-fr-13).
- **BR-05.** Оборудование выдаётся бригаде в офисе в начале дня на весь день; передача оборудования между бригадами возможна только при личной встрече (учитывается как допущение модели, не мешает MVP).

### 4.2. Квалификация и ресурсы

- **BR-06.** Навык — тип заявок, который может выполнять бригада (справочник: локальные работы / подключения и дозаказы / аварии). У бригады от 1 до 3 навыков одновременно. Справочник «бригада → навыки» и «бригада → доступный транспорт» составляется самостоятельно (в данных не задан явно).
- **BR-07.** Если у бригады нет нужной квалификации — заявка ей не может быть назначена ни при каких условиях.
- **BR-08.** Тип транспорта бригады синтетически распределяется по любой доле (автомобиль/пешеход/велосипед/общественный транспорт). Если у заявки указан требуемый тип транспорта — назначенная бригада обязана иметь именно этот тип.
- **BR-09.** Приоритет при назначении — не кратчайшее расстояние, а наименьшее время прибытия с учётом скорости конкретного вида транспорта (пеший маршрут может быть короче, но медленнее автомобильного).
- **BR-10.** Пробег/время в пути считается по дорожной сети (граф дорог, например OpenStreetMap), а не по прямой (Евклидово расстояние запрещено как основной способ расчёта).
- **BR-11.** Учёт оборудования — правило модели *для дополнительной возможности FR-20* (ТЗ п.2.2 прямо называет учёт оборудования «дополнительным усложнением» сверх трёх обязательных ограничений, поэтому в обязательный MVP это правило не входит, см. §7): если/когда FR-20 реализуется, при (пере)планировании на бригаду можно назначать только те заявки, для которых у неё достаточно оборудования; допустимый запас определяется самостоятельно.

### 4.3. Приоритизация и перепланирование

- **BR-12.** Приоритет типов работ: **Авария → Подключение → Ремонт/Дозаказ**. Аварии и новые подключения — в первую очередь, остальное — по остаточному принципу.
- **BR-13.** Аварию нужно выполнить максимально быстро; аварийная заявка может вытеснять уже назначенные заявки бригады, если это не нарушает их временные окна, и может привести к перепланированию оставшейся части рабочего дня (условие №48). Начатую работу авария не прерывает (BR-32).
- **BR-14.** Норматив выполнения аварии — **100 минут** (см. также [`07_data_dictionary.md`](07_data_dictionary.md)); отсчёт времени начинается с момента фактического поступления заявки в систему в течение дня (не с начала смены). По условию **№45** норматив складывается из **20 мин на дорогу до ТКД + 80 мин работы на объекте**. Норматив на дорогу — величина переменная: 20 минут — резерв, которым заявка бронирует время в графике при постановке; при распределении он заменяется на реально рассчитанное по дорожной сети время в пути (BR-10). Увеличение резерва допустимо, но редко (параметр модели). Это же правило действует для компонента «Дорога до клиента» остальных типов заявок (раздел 8 [`05_spec_backend.md`](05_spec_backend.md#8-модуль-расчёта-нормативов-длительности)).
- **BR-15.** Перепланирование в течение дня возможно и ожидаемо. Триггеры: новая срочная заявка (авария), новая обычная заявка (подключение, локальная заявка, дозаказ — условие №47), отмена заявки, недоступность бригады. Новая обычная заявка перестройку плана не вызывает (BR-31), авария — может (BR-13).
- **BR-16.** При перепланировании ранее согласованное с клиентом время может быть скорректировано; уведомление клиента — зона ответственности службы поддержки, вне системы.
- **BR-17.** Хороший алгоритм перепланирования вносит **минимально необходимое** изменение в расписание, а не пересобирает весь день заново (метрика `PlanStability`).
- **BR-18.** Базовый сценарий MVP — статическое планирование на основе исходной выгрузки; динамическое перепланирование — поддерживаемая, но не обязательная для каждого тика возможность.
- **BR-19.** Метрика простоя бригады фиксируется, но не используется в оптимизации на этапе MVP.
- **BR-30.** Внутри региона территории (Москва и удалённые города Подмосковья — Домодедово, Кашира, Ступино и т.п.) назначение не ограничивают: московскую бригаду можно отправить в удалённый город, а бригаду из области — на работы в Москве, если это рационально (условие №46). Нежелательно, чтобы бригада в течение дня без необходимости «кочевала» между удалённым городом и Москвой (например, «Москва → Домодедово → Москва → Домодедово»): маршрут должен оставаться рациональным. Специального запрета нет — такие маршруты отсекает минимизация времени в пути (критерий №3 раздела 3).
- **BR-31.** Новая обычная (неаварийная) заявка, появившаяся в течение дня, добавляется в расписание бригады, только если помещается в свободный интервал между уже запланированными работами без нарушения их окон; уже сформированный план она не перестраивает и ничего не вытесняет. Если свободного интервала нет ни у одной подходящей бригады — заявка остаётся неназначенной с причиной (условие №47).
- **BR-32.** Инженер не бросает начатую работу: заявка в статусе `В работе` при перепланировании не снимается и не переносится; бригада освобождается только после её завершения по нормативу. Заявки, к выполнению которых бригада ещё не приступила (включая `В пути`), перестраивать можно (условие №48).
- **BR-33.** Для аварии закладывается ориентировочное время реакции — от поступления заявки до прибытия бригады — **1–2 часа** (параметр модели, по умолчанию 120 мин; условие №49). Бригада для аварии выбирается с учётом времени появления аварии, текущего состояния исполнителей (где находятся, когда освободятся) и требуемого времени реакции. Время реакции — целевое, а не жёсткое: если ни одна бригада не успевает, авария назначается бригаде с самым ранним прибытием, а превышение показывается в объяснении.

### 4.4. Временные окна и время

- **BR-20.** Временное окно заявки (начало/окончание) — время, в которое клиент готов ждать мастера; клиент сообщает его при оформлении заявки, ещё до построения плана. Сдвигать окно нельзя: бригада обязана прибыть строго в интервал. Фиксированные окна — базовый сценарий; эксперимент с их изменением допустим, если он показывает рост эффективности (условие №50, FR-33).
- **BR-21.** Всё время хранится в БД без временной зоны и без избыточной точности. Часовой пояс определяется клиентом (фактически — регионом). В синтетических данных используется московское время.
- **BR-22.** Обеденные и технические перерывы бригад **не учитываются** в MVP — отдельная задача после MVP.
- **BR-23.** Заявка «Отменена» в синтетических данных означает, что клиент отменил её **после** попадания в график бригады (после выезда/прибытия исполнителя), а не до назначения.

### 4.5. Жизненный цикл заявки и данные

- **BR-24.** Статусы заявки: `Отправлена` (заявка передана исполнителю) → `В пути` → `В работе` → `Завершено`; альтернативная ветка — `Отменена` (отказ клиента или невозможность выполнения по факту).
- **BR-25.** Факт закрытия (выполнения/отмены) заявки фиксирует диспетчер на основании сообщения от бригады. Закрытые заявки считаются финальными и не участвуют в последующем перепланировании.
- **BR-26.** Зависимостей между заявками нет: закрытие одной заявки не закрывает другие. Заявка не требует выезда более одной бригады.
- **BR-27.** Поля «Тип заявки ВК» (Beekeeper) и «Тип заявки HD» (HelpDesk) — это одна и та же заявка, обозначенная в разных исходных системах, а не два вида работ; соответствие между классификаторами команда определяет самостоятельно (см. [`07_data_dictionary.md`](07_data_dictionary.md)).
- **BR-28.** Если входных данных не хватает для модели (компетенции, транспорт, оборудование) — их необходимо синтезировать самостоятельно и явно задокументировать допущения.
- **BR-29.** В расчётах и экспериментах используются только синтетические данные; контрольное распределение — не эталон и не цель повторения, а лишь пример возможного результата для сверки порядка величин.

| FR-26 | Прогноз риска опоздания/нарушения SLA по заявке | C | ТЗ п.2.5, `application.md` |
| FR-27 | Учёт комбинированных способов перемещения (в т.ч. общественный транспорт) с реалистичным расчётом маршрута | C | conditions §40 |
| FR-28 | Управление жизненным циклом статусов заявки (Отправлена/В пути/В работе/Завершено/Отменена/Просрочена) и фиксация факта закрытия диспетчером | M | conditions §27–28, 34; BR-24, BR-25 |
| FR-29 | Хранение времени как наивного (без временной зоны) локального времени в БД; часовой пояс определяется клиентом/регионом, отображение и обработка — в этом поясе | M | conditions §17; BR-21 |
| FR-30 | Изоляция данных и планирования по регионам (3 независимых сценария, регион = CSV-файл); внутри региона назначение между Москвой и удалёнными городами не ограничивается | M | BR-03, BR-30 |
| FR-31 | Адаптация интерфейса диспетчера под мобильные устройства (responsive) | M | conditions §25 |
| FR-32 | Динамическое перепланирование как расширяемая возможность поверх статического MVP-плана | S | conditions §35 |
| FR-33 | Эксперимент с изменением временных окон: сравнение метрик плана при фиксированных и расширенных окнах | C | conditions §50; BR-20 |
| FR-34 | Добавление новой обычной заявки в течение дня в свободный интервал бригады без перестройки плана | S | conditions §47; BR-31 |

> **Правило присвоения приоритета.** Требование мандаторно (M), если хотя бы один источник (ТЗ или `conditions.md`) формулирует его императивно («надо», «нужно», «должен», «необходимо») и ни ТЗ, ни `conditions.md` явно не помечают его как дополнительное/необязательное/послеMVP-задачу. Явная пометка «дополнительно/опционально» хотя бы в одном из двух источников понижает приоритет, даже если во втором такой пометки нет (пример — FR-20: `conditions.md` формулирует учёт оборудования как факт, но ТЗ раздел 2.2 прямо называет его «дополнительным усложнением» сверх трёх обязательных групп ограничений).

## 6. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | Объяснения решений формулируются на естественном языке без терминов алгоритма (не «penalty cost», а «нет свободного времени у бригады») |
| NFR-02 | Целевой объём данных для демонстрации — 10–15 бригад, не более 100 заявок в день; построение плана и объяснений должно укладываться в интерактивное время демонстрации (секунды–единицы минут) |
| NFR-03 | Решение воспроизводимо по инструкции в README без ручных доработок |
| NFR-04 | Не требуется: промышленная отказоустойчивость, очереди сообщений (Kafka), микросервисная архитектура, авторизация/аутентификация, нагрузочное тестирование на тысячах заявок, полноценное мобильное приложение (нативное) |
| NFR-05 | Запуск возможен локально; Docker — по желанию; публичный демо-стенд приветствуется |
| NFR-06 | Код и алгоритм должны быть проверяемы: юнит-тесты на обязательные ограничения (квалификация/время/ресурс) |
| NFR-07 | Интерфейс понятен без чтения кода: результат плана и причины решений читаемы диспетчером напрямую в UI |

## 7. Границы MVP и развитие

| Уровень | Состав |
|---|---|
| **Обязательный MVP** | FR-01…FR-19, FR-23, FR-28…FR-31 — распределение заявок, три группы обязательных ограничений, маршруты на карте, одно событие перепланирования, понятное объяснение результата, расчёт обязательных метрик, сравнение с базовым алгоритмом, наблюдаемая метрика простоя и корректная работа со временем клиента/региона |
| **Дополнительные возможности** | FR-20…FR-22, FR-24…FR-27, FR-32…FR-34 — учёт оборудования, балансировка и стабильность плана, ручное переназначение, несколько сценариев изменений, прогноз опозданий/SLA, биоинспирированная локальная доводка маршрута ([`08_algorithm.md`](08_algorithm.md#6-необязательные-расширения)), общественный транспорт, эксперимент с гибкими окнами, вставка новой обычной заявки в течение дня |

## 9. Открытые бизнес-вопросы (вне зоны MVP, зафиксировать как допущения)

- Формат и канал уведомления клиента службой поддержки при сдвиге окна — не проектируется в MVP, система лишь помечает затронутые заявки.
- Учёт обеденных/технических перерывов бригад — заложить точку расширения в модели смены, не реализовывать в MVP (BR-22).
- Учёт передачи оборудования между бригадами при личной встрече — допускается как упрощение (весь запас выдан утром), полноценный трекинг передачи — вне MVP.
