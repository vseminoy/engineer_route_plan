# Технологии и стек решения

## 1. Принципы выбора

1. Разрешено организатором и не избыточно: без Kafka, микросервисов, промышленной отказоустойчивости, авторизации (ТЗ п.3.2).
2. Готовая библиотека для VRPTW-ядра вместо написания солвера с нуля (ТЗ п.2.3 — «не требуется доказывать математический оптимум»).
3. Расстояние/время — по дорожной сети, а не по прямой (BR-10) → нужен граф дорог и матрица маршрутов.
4. Стек воспроизводим локально за разумное время установки (ноутбук участника + интернет, ТЗ п.3.1).
5. Совместим с направлением, заявленным в `application.md` (Python/FastAPI/React/PostgreSQL+PostGIS/OR-Tools или VROOM/OSM+OSRM/ML), чтобы не расходиться с презентованным жюри подходом.

## 3. Backend

| Компонент | Технология | Обоснование |
|---|---|---|
| Язык/рантайм | Python 3.11+ | Заявлено в ТЗ как пример; лучшая экосистема для OR-Tools/науки о данных |
| Web-фреймворк | FastAPI | Асинхронность, автогенерация OpenAPI-схемы (нужна фронтенду и для документации), Pydantic-валидация входных данных |
| Валидация/схемы | Pydantic v2 | Строгая проверка форматов заявок/бригад/событий из ТЗ п.2.4 |
| Оптимизационное ядро | **Google OR-Tools** (`ortools.constraint_solver.routing`) | VRPTW из коробки: временные окна, несколько ТС, дизъюнкции (разрешить неназначенные заявки со штрафом), кастомные ограничения через callbacks (навык = допустимость узла для агента, оборудование, приоритет). Гибче VROOM для специфичных бизнес-правил (BR-12…BR-14) на Python. См. сравнение в разделе 4 |
| Доступ к данным | **aiosql** + `psycopg` в качестве драйвера | Аналог `sqlc` для Python: SQL живёт в `.sql`-файлах с именованными запросами (`-- name: get_engineer^`), в коде вызывается как метод объекта `queries` (`queries.get_engineer(conn, id=3)`). Не ORM — полный контроль над SQL, нет скрытой генерации запросов; выбрано вместо SQLAlchemy ORM по явному решению команды |
| Миграции схемы | Alembic **без ORM-моделей**, только raw-SQL миграции (`op.execute(...)`) | Alembic поддерживает миграции без декларативных моделей; используется исключительно для версионирования DDL, не для построения запросов — эту роль полностью закрывает aiosql |
| Роутинг/матрица расстояний | Клиент к **OSRM** (`/table`, `/route`) поверх OSM-данных региона | Реальный граф дорог вместо прямых линий (BR-10); скорость профиля зависит от типа транспорта (BR-08, BR-09) |
| Фоновые задачи (опционально) | `BackgroundTasks` FastAPI на MVP; Celery/RQ — точка расширения | Объём заявок (≤100) не требует очереди для MVP; синхронного пересчёта достаточно |
| Тесты | pytest + pytest-cov | NFR-06: проверка обязательных ограничений (квалификация/время/ресурс) |
| Логирование/конфиг | **structlog** поверх stdlib `logging` + Pydantic `BaseSettings` | Структурированное логирование (аналог `slog` в Go): у записи стабильное имя события и поля ключ–значение, `request_id`/`run_id` подставляются из контекста; JSON в `stdout` на стенде, человекочитаемый вывод при локальной разработке; логи uvicorn/alembic/httpx выходят в том же формате. Наблюдаемость без внешних систем |

## 4. Выбор оптимизационного ядра

Статическая задача (`08_algorithm.md` §1) одновременно требует четырёх свойств: (1) жёсткие навыки/тип транспорта как ограничение допустимости, (2) жёсткие временные окна, (3) первичная цель — минимум задействованных бригад, а не расстояние, (4) допустимость частичного покрытия — низкоприоритетную заявку можно оставить неназначенной. Сравнение открытых инструментов по этим четырём свойствам (методология и источники — [`08_algorithm.md` §2](08_algorithm.md#2-обзор-инструментов-и-обоснование-выбора)):

| Инструмент | Навыки (жёстко) | Врем. окна | Мин. кол-во ТС как цель №1 | Частичное покрытие | Развёртывание |
|---|---|---|---|---|---|
| **Google OR-Tools** RoutingModel | ✅ `SetAllowedVehiclesForIndex` | ✅ dimension | ✅ реализуемо через фазовую оптимизацию (`08_algorithm.md` §4.1) | ✅ `AddDisjunction` + штраф | In-process в Python-backend |
| VROOM | ✅ нативный `skills` | ✅ | ⚠️ не декларативная цель «из коробки» | ✅ нативно, `priority` | Отдельный HTTP-сервис, как OSRM |
| PyVRP | ⚠️ hard vehicle-client compatibility — только в Enterprise-версии | ✅ | дружелюбно по духу архитектуры | ✅ нативно (prize-collecting/team-orienteering) | In-process в Python-backend |
| jsprit | ✅ нативно, `HardSkillConstraint` — самая прямая реализация | ✅ | реализуемо тем же приёмом, что и в OR-Tools | частично | Отдельный JVM-сервис, как OSRM |
| `alns` (фреймворк, не готовый солвер) | реализуется самостоятельно | реализуется самостоятельно | реализуется самостоятельно | реализуется самостоятельно | In-process в Python-backend |

**Решение:** кастомная модель на **OR-Tools RoutingModel** — единственный проверенный вариант, покрывающий все 4 свойства без дополнительного сервиса и без лицензионных ограничений. jsprit остаётся равноценной альтернативой (решает навыки нативнее ценой отдельного JVM-сервиса на стенде); `alns` — резервный вариант, если конструктор ограничений OR-Tools окажется слишком жёстким при реализации приоритетного вытеснения аварией (BR-13); VROOM — резервный вариант при отказе от минимизации флота как отдельной декларативной цели.

**Baseline-алгоритм** (обязателен по ТЗ п.2.3 для сравнения) — последовательный проход по заявкам в порядке поступления, назначение первому подходящему по порядку исполнителю без глобальной оптимизации порядка посещения.

## 6. Frontend

| Компонент | Технология | Обоснование |
|---|---|---|
| Фреймворк | React 18 + TypeScript | Заявлено в `application.md`; типизация снижает риск рассинхронизации с backend-контрактом |
| Сборка | Vite | Быстрый старт для хакатон-таймлайна |
| Состояние/данные | Zustand (локальный UI-стейт) + TanStack Query (кэш и синхронизация с REST API) | Просто, без boilerplate Redux, достаточно для объёма экранов MVP |
| Клиент API и валидация форм | **orval** (генерация из `back/openapi/openapi.yaml`): fetch-клиент с типами + zod 4-схемы | Типы, клиент и ограничения полей форм берутся из той же спеки, что и валидация на backend, — без ручной копии. Выбран по пробной генерации: единственный из кандидатов (hey-api/openapi-ts, openapi-zod-client), кто переносит `additionalProperties: false` (`strictObject`) и при этом разбирает спеку из нескольких файлов; ответы ошибок типизированы по кодам (`400` → `ValidationError`) |
| Карта | `react-leaflet` + OpenStreetMap tiles | См. раздел 5 |
| UI-кит | Ant Design (или MUI) с адаптивной сеткой | Готовые таблицы/списки/модалки ускоряют MVP; обе библиотеки поддерживают responsive из коробки |
| Адаптивность | Mobile-first CSS (флекс/грид, точки перелома ≤768px) | Обязательное условие §25 — фронт адаптирован под мобильные устройства |
| Тесты | Vitest + React Testing Library | Базовая проверка ключевых компонентов (карта, панель объяснений) |

> Нативное мобильное приложение не требуется (ТЗ п.3.2, NFR-04) — «адаптация под мобильное» реализуется как responsive web (при желании — PWA), а не отдельный клиент.

## 8. Инфраструктура и запуск

- **Локальный запуск:** `uvicorn` для backend (требует запущенный локально PostgreSQL), `vite dev` для frontend — без контейнеров, для быстрой отладки.
- **Docker Compose:** сервисы `backend`, `frontend`, `db` (PostgreSQL + PostGIS), `osrm` — один `docker compose up` поднимает весь демо-стенд, включая граф дорог региона. Стенд доступен с ранних этапов разработки: ещё не реализованные эндпоинты отвечают `501 not_implemented`. Для запуска Docker не обязателен (NFR-05) — остаётся локальный запуск выше.
- Публичный демо-стенд — опционально, приветствуется организатором, не обязателен.
